# 延期能力与升级门总账

## 1. 文档定位

本文档记录项目中“当前暂不单独立项、先并入其他专项或模块承接，但未来可能需要升级”的能力。

它不是产品需求清单，也不是模块内部派单清单。它的作用是让新线程、新 agent 和后续 PR 审查能主动发现前期工程折中，并在正确时机复核是否需要升级。

登记规则见 `docs/工程方法与规范/延期能力与升级门规则.md`。

## 2. 状态标记

| 标记 | 含义 |
|---|---|
| `[deferred]` | 已延期，有承接位置或后续检查点 |
| `[watch]` | 观察中，当前不单独立项，但必须在指定时机复核 |
| `[covered]` | 承接专项已覆盖最低要求，暂不拆分 |
| `[split]` | 已触发升级，进入独立专项、模块或质量门 |
| `[closed]` | 已关闭，不再继续跟踪 |

### 3.1 候选条目识别口径

本总账当前以 `S-05` 为试点条目；后续 agent 在以下场景**必须主动判断是否新建延期能力条目**：

- 跨域总账 §7 中专项被标为"不单独立项 / 并入其他专项 / 待启动"，但仍有不可丢失的最小必须覆盖项时。
- 模块推进清单 §7 "需反馈系统总调度的事项"中产出"承接专项后续负责"的结论时。
- PR 审查中发现某项业务能力被工程插槽 / 横切专项承接，但承接文档只覆盖工程边界、未覆盖业务语义 / 失败补偿 / 人工接管 / 验收口径时。
- 顶层基线、模块规格或专项设计中出现"先支持最小形态、未来再扩展"的表述时。

候选条目示例（不强制立刻新建，但发现时应判断）：

- `S-02 User 治理与纠错专项`：当前不强制启动；若学生 / 教师建档批量出现疑似重复 `User` 而无统一治理入口，应升级。
- `S-03 通知与消息能力专项`：当前各模块只产生通知意图；若三个以上业务域出现共用模板 / 通道 / 失败重试需求，应升级。
- `S-04 统一后台调度专项`：当前由 `S-05` 同时覆盖任务调度；若审批超时、考勤判缺、长假确认等扫描类任务需要统一并发锁、跨实例编排或统一观察台，应升级。
- `S-07 设备接入专项`：当前以模拟事件接入；真实设备型号 / 拓扑 / 验收用例齐备时升级。
- `S-13 数据生命周期管理专项`：当前 P2 暂缓；若审计、归档或合规删除出现强约束，应升级。

新建条目流程：系统总调度或模块开发总控判断 → 在本表新增一行 → 同步回写 `跨域依赖收口总账 §7` 对应专项的状态描述 → 在 `AGENTS.md` 中无需新增引用（已索引本总账）。

## 4. S-05 跨域任务与事件可靠性机制

### 4.1 当前不单独立项的依据

`S-05` 当前不是一个独立业务域，而是后端工程骨架和运行保障共同承接的横切能力：

- 后端工程骨架负责提供 `cross_domain_task / event_outbox / EventEmitter2 / BullMQ` 的工程插槽、模块边界、worker 分层和调用方式。
- 运行保障、日志与可观测性专项负责失败可发现、可追踪、可重试、可告警和可人工接管。
- 当前阶段还没有足够多的真实业务链路沉淀统一状态机、统一后台处理台或统一事件订阅治理模型。

因此，本阶段不新建独立 `跨域任务与事件可靠性专项设计.md`。PR `#17` 合并后，`S-BE-01` 与 `S-BE-07` 已共同覆盖 `S-05` 的文档验收条件，状态从 `[watch]` 更新为 `[covered]`。

`[covered]` 只表示当前文档层验收已覆盖，不表示后续工程实现可跳过检查。若工程落地或安全到校纵切中触发 §4.3 条件，仍必须升级为独立横切专项。

### 4.2 最小必须覆盖项

两个承接专项合起来至少必须覆盖：

- `cross_domain_task` 的任务注册、任务类型、业务关联键、状态、重试次数、最后错误和人工接管入口。
- `event_outbox` 的事件写入、发布、幂等键、投递状态、失败记录和重试边界。
- `EventEmitter2` 与 `BullMQ` 的使用边界：哪些是进程内非可靠编排，哪些必须走可靠异步事件或队列。
- worker / publisher 的分层边界、命名约定、并发控制和失败处理。
- 死信、补偿、重放、人工接管和排障入口。
- 任务日志、事件投递日志、`traceId / requestId / jobId / eventId` 串联规则。
- 告警边界：哪些失败必须告警，哪些失败只记录诊断日志，哪些失败必须进入人工处理。

### 4.3 升级触发条件

满足以下任一条件，`S-05` 必须从当前状态升级为 `[split]`，新建独立横切专项：

- 需要定义统一跨域任务状态机，而不是仅由各 worker 自行约定状态。
- 出现三个以上业务域共用同一类补偿、重试、人工接管或重放流程。
- `event_outbox` 需要统一事件命名、payload schema、订阅规则、版本兼容或废弃策略。
- 需要建设统一后台处理台、统一死信队列处理入口或统一任务补偿页面。
- 后端工程骨架只覆盖工程插槽，运行保障专项只覆盖日志告警，二者之间没有文档负责“任务语义 + 补偿闭环”。
- 安全到校纵切或后续端到端链路发现跨域任务失败后无法定位责任边界。

升级后的建议落点：

`docs/10-横切专项设计/XX-跨域任务与事件可靠性专项设计.md`
