# 新项目初始化指南

本文说明一个刚开始的项目如何接入 GanttMD。

## 第一步：安装并初始化

本仓库本地开发时先安装 CLI：

```bash
npm install -g .
```

发布后可使用：

```bash
npm install -g ganttmd
```

在项目根目录初始化：

```bash
ganttmd init
```

初始化后项目内只需要保存数据目录：

```text
.ganttmd/
  config.yaml
  followups.md
  runs.md
  tasks/
```

`ganttmd init` 不覆盖已有文件，只补齐缺失的最小骨架。

## 第二步：写 config.yaml

最小示例：

```yaml
project:
  id: demo
  name: 示例项目
ganttmd:
  schema_version: 1

milestones:
  - id: M1
    name: 项目骨架建立
    status: in_progress
    description: 明确需求边界、工程骨架和最小闭环

  - id: M2
    name: 第一条业务闭环
    status: backlog
    description: 完成一条可验收的端到端业务链路

  - id: M3
    name: 扩展与治理
    status: backlog
    description: 补齐质量、权限、审计和部署治理
```

里程碑建议控制在 3-5 个。不要把每个模块都写成里程碑。

如果项目已有完整路线图，可以把暂时没有任务的里程碑也写入 `config.yaml`。页面会显示为 `0 任务 · 未拆解`，表示路线图存在但还没有拆到执行任务。

## 第三步：创建任务文件

按维护便利创建任务文件，例如：

```text
.ganttmd/tasks/
  product.md
  backend.md
  frontend.md
  qa.md
```

任务文件不是代码模块的一比一映射，只是任务容器。可以按工作主线、业务域、活跃状态或团队习惯拆分。一个任务文件里建议先放 3-8 个任务。

## 第四步：写第一批任务

任务使用 fenced code block：

````markdown
### S-BE-01 后端工程骨架专项设计

```ganttmd-task
id: S-BE-01
title: 后端工程骨架专项设计
status: todo
dependencies: []
milestone: M1
track: backend
domain: foundation
priority: P0
source_docs: [docs/需求说明.md]
next_action: 明确后端目录、模块边界和启动入口
acceptance: [目录结构确定, 本地启动路径明确, 后续实现任务可承接]
evidence: []
```

补充说明写在任务块外面。
````

任务块内放结构化字段。任务块外可以写人类可读说明。

## 第五步：写 AGENTS.md

把 `docs/Agent协作规则模板.md` 的内容复制到项目根目录 `AGENTS.md`，再按项目实际情况改路径和限制。

Agent 不会天然知道 GanttMD 的存在，必须通过 `AGENTS.md` 明确告诉它：

- 任务文件在哪里。
- 怎么判断可领取任务。
- 怎么领取。
- 怎么完成。
- 什么情况下不能改任务状态。

## 第六步：校验并打开本地看板

在项目根目录运行：

```bash
ganttmd validate
ganttmd doctor
```

然后登记项目并启动看板：

```bash
ganttmd project add .
ganttmd serve
```

在本地看板检查：

- 任务是否被读取。
- 里程碑是否显示。
- 执行视角是否能看到可执行任务。
- 依赖阻塞是否符合预期。
- 健康检查是否提示缺字段。
- Follow-up 视图是否能正常显示 `.ganttmd/followups.md`。

起步阶段应先保证没有警告，再让 Agent 按 `AGENTS.md` 领取任务。

## 起步建议

新项目第一天不要写太细。

推荐起步规模：

- 3 个里程碑。
- 2-4 个任务文件。
- 10-20 个任务。
- 每个任务只写必要字段。

等项目真实推进一轮后，再补 `next_action`、`acceptance`、`source_docs` 的细节。
