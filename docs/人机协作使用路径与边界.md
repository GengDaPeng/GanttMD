# 人机协作使用路径与边界

本文档从真实使用路径出发，说明人类负责人和 AI Agent 如何共同使用 GanttMD，以及哪些边界不能混淆。

GanttMD 的定位不是通用项目管理系统，而是 AI Agent 参与开发时的任务状态层。它要解决的问题是：项目状态能被人看懂，也能被 Agent 稳定读取、更新和校验。

## 1. 核心原则

### 1.1 真相源边界

`.ganttmd/` 是任务状态真相源，只保存任务、依赖、状态、证据链、阻塞和 follow-up。

正式需求、技术设计、数据模型、接口清单、测试规范、PR 讨论和长篇方案不应搬进 GanttMD。GanttMD 只通过 `source_docs`、`source_pr`、`source_rr`、`source_commit` 引用它们。

### 1.2 写权限边界

普通 Agent 可以：

- 领取任务。
- 更新自己正在执行的任务状态。
- 补充 `evidence`、`verification`、`review_status`。
- 追加新的 open follow-up。
- 对已有 follow-up 追加补充说明或证据。

普通 Agent 不得：

- 删除任务。
- 大范围重排任务文件。
- 关闭 follow-up。
- 把 follow-up 转成正式任务。
- 把用户裁决、延期接受或取消决定写成既成事实。

项目主控可以：

- 新增、合并、拆分、取消任务。
- 清理 follow-up。
- 将 follow-up 转成正式任务。
- 接受延期并设置复核时间。
- 裁决任务是否真实完成。

### 1.3 完成态边界

`done` 不等于 Agent 口头说“完成了”。

任务进入 `done` 至少应满足：

- 有 `evidence`。
- 工程类任务有 `verification`。
- 需要复核的任务有 `review_status`。
- 如产生剩余事项，已登记到 `.ganttmd/followups.md`。

如果任务已有产出但还在等待 PR、复核或用户判断，应使用 `status: review`。

### 1.4 阻塞边界

阻塞优先由依赖派生。一个 `todo` 任务如果存在未完成前置依赖，看板可显示为被阻塞。

外部阻塞、用户裁决、资料等待和延期接受不应滥用 `status: blocked`。这些事项应通过 `blocked_reason`、follow-up 或风险项表达。

### 1.5 延期边界

“后续再做”“以后优化”“暂不处理”“本轮不修”不能只留在聊天总结或 PR 回复里。

只要这类事项会影响后续交付、验收、风险或用户判断，就必须登记到 `.ganttmd/followups.md`。

`accepted`、`deferred`、`external_wait` 等长期事项必须有 `next_review_at` 或明确触发条件，否则会变成新的沉没清单。

## 2. 人类负责人使用路径

### 2.1 首次接入

人类负责人接入一个项目时，应完成以下动作：

1. 创建 `.ganttmd/config.yaml`。
2. 创建 `.ganttmd/tasks/*.md`。
3. 创建 `.ganttmd/followups.md`。
4. 从仓库 `tools/ganttmd/` 复制 `index.html` 与 `rules.js` 到项目的 `.ganttmd/` 目录（与 config.yaml / tasks/ 同级）。
5. 将 GanttMD 规则写入项目 `AGENTS.md`。
6. 打开页面，选择项目目录。
7. 运行校验命令：

```bash
npm run validate -- .
```

最低接入成功标准：

- 页面能读取任务。
- 里程碑能显示。
- 执行视角能看到任务队列。
- 风险视角能看到阻塞和健康检查。
- Follow-up 视角能显示清单。
- validate 没有 warning。

### 2.2 日常查看

人类负责人日常主要看 5 件事：

- 当前正在做什么。
- 下一步建议做什么。
- 哪些任务卡住了。
- 哪些事项需要用户裁决。
- 哪些 follow-up、延期项或外部等待还没清理。

默认不应要求人类负责人阅读所有字段、所有 PR 评论、所有测试输出。页面应先展示判断摘要，再允许点开追溯证据。

### 2.3 主控清理

项目主控应定期清理：

- open follow-up。
- accepted follow-up。
- 外部等待。
- 用户裁决。
- 超期未复核事项。
- 长期 in_progress 任务。
- review 状态但无复核结论的任务。

清理结果只能有几类：

- 转正式任务：写入 `.ganttmd/tasks/*.md`，follow-up 改为 `converted`。
- 继续等待：补 `next_review_at` 和原因。
- 已处理：补 `resolution`，改为 `done`。
- 明确不做：补 `resolution`，改为 `wontfix`。
- 需要用户裁决：保持 open 或 accepted，并明确 `decision_owner`。

### 2.4 判断真实完成

主控判断任务是否完成时，应先看：

- `evidence` 是否存在。
- `verification` 是否足够。
- `review_status` 是否说明复核结论。
- 是否产生未登记 follow-up。
- 下游任务是否会被本次实现方式阻塞。

如果缺关键证据，任务不应进入 `done`。可以先进入 `review`，等待补证据或复核。

## 3. Agent 使用路径

### 3.1 进入项目

Agent 开始工作前必须先读取：

1. 项目 `AGENTS.md`。
2. `.ganttmd/config.yaml`。
3. `.ganttmd/tasks/*.md`。
4. `.ganttmd/followups.md`。

如果项目提供校验脚本，应先运行：

```bash
npm run validate -- .
```

Agent 不应跳过 GanttMD 直接根据聊天上下文自行决定下一步。

### 3.2 选择任务

Agent 优先选择：

- `status: todo`。
- 所有 `dependencies` 已完成。
- `source_docs` 明确且可读取。
- `next_action` 明确。
- `acceptance` 明确。

Agent 不应领取依赖未完成、来源文档缺失、验收边界不清晰的任务。遇到这种情况，应先补字段、推进前置任务，或登记问题交给主控。

### 3.3 领取任务

领取任务时，Agent 应更新：

```yaml
status: in_progress
agent: codex
start_date: 2026-05-23
```

如果已经存在其他 `agent` 或 `owner`，应先确认是否接手、并行或冲突，不能直接覆盖。

### 3.4 执行任务

执行时，Agent 应按以下顺序推进：

1. 阅读 `source_docs`。
2. 对照 `next_action` 明确本轮工作范围。
3. 对照 `acceptance` 判断完成边界。
4. 检查 `downstream_constraints`，避免破坏下游任务。
5. 实施改动。
6. 运行必要验证。
7. 更新任务证据链。

如果执行中发现任务定义错误，应先更新 GanttMD 或向主控说明，而不是绕过任务继续做。

### 3.5 提交前

Agent 提交前应运行：

```bash
npm run validate -- .
```

如果 validate 出现 warning，优先修复 `.ganttmd/`，不能只在回复里解释。

提交说明应包含：

- 修改了哪些任务。
- 哪些任务进入 review 或 done。
- 新增了哪些 evidence。
- 是否新增 follow-up。
- 是否还有阻塞或用户裁决。

### 3.6 完成或复核

如果任务已经完成但需要复核，应写：

```yaml
status: review
review_status: pending
evidence: [PR#27]
```

如果任务真实闭环，应写：

```yaml
status: done
evidence: [PR#27, commit:abcdef]
verification: pnpm test
review_status: passed
```

如果任务不做，应写：

```yaml
status: cancelled
cancel_reason: 明确取消原因
resolution: 后续如何处理
```

## 4. PR 与 Follow-up 路径

### 4.1 PR 中产生 follow-up

PR 评论区出现以下情况时，必须登记 follow-up：

- `[REVIEW]` 提出可延后项。
- `[FIX-REPLY]` 写“后续处理”。
- `[RECHECK]` 发现还有尾项但允许合并。
- `[MERGE-READY]` 前仍有不影响合并的剩余风险。

来自 PR 的 follow-up 必须填写：

```yaml
source_type: pr_review
source_pr: PR#27
source_rr: RR-003
```

没有 `source_pr` 和 `source_rr` 的 PR follow-up 视为不可追溯。

### 4.2 Follow-up 转正式任务

只有项目主控可以把 follow-up 转成正式任务。

转换时应：

1. 在 `.ganttmd/tasks/*.md` 新增正式任务。
2. 填写任务 `source_docs` 或 PR 来源。
3. 给任务分配 `milestone`、`track`、`domain`。
4. 将 follow-up 改为 `converted`。
5. 填写 `converted_task` 和 `resolution`。

普通 Agent 只能建议转换，不能直接转换。

## 5. 校验路径

校验器的目标不是替代人判断，而是防止结构性错误进入任务真相源。

当前校验重点：

- 任务 ID 重复或缺失。
- 依赖指向不存在任务。
- 任务缺少 `milestone` 或 `track`。
- 任务引用未知里程碑。
- `source_docs` 指向不存在文档。
- `done` 缺少 `evidence`。
- 工程类 `done` 缺少 `verification`.
- `review` 缺少 `review_status`。
- PR follow-up 缺少 `source_pr` 或 `source_rr`。
- accepted follow-up 缺少主控、决策或复核时间。

后续校验器应继续补：

- 任务超过 N 天未更新。
- `in_progress` 长期无人认领或 owner 不明确。
- L2 / 高风险任务缺少复核状态。
- follow-up 超过 `next_review_at` 未处理。
- evidence 中 PR / commit 格式不规范。
- 页面健康检查和 CLI 校验结果共用同一套规则。

## 6. 当前已覆盖能力

当前 GanttMD 已具备：

- Markdown 任务真相源。
- 静态只读看板。
- 执行、里程碑、主线、模块、风险、Follow-up 视图。
- 任务依赖展示。
- Agent 指令草案。
- follow-up 类型和状态治理。
- 证据链字段。
- 命令行校验脚本。
- jwxt-lite 真实感样例。

## 7. 当前缺口

### 7.1 使用闭环缺口

- 缺少完整接入检查清单。
- 缺少主控定期清理 SOP。
- 缺少 PR 评论区到 follow-up 的具体模板。
- 缺少真实项目首次迁移步骤。

### 7.2 工具能力缺口

- 页面健康检查和 CLI 校验器规则尚未完全复用。
- CLI 还不能输出推荐任务。
- CLI 还不能自动生成接手指令。
- 页面不能直接运行本地校验脚本，只能展示内置健康检查。

### 7.3 Schema 缺口

- 任务层级、任务类型和风险等级还可以更严格。
- evidence 的格式暂时宽松。
- verification 的结构化程度不足。
- accepted / deferred / external_wait 的复核规则还可以更细。

## 8. 下一阶段优先级

### P0：真实接入闭环

- 从 jwxt 当前文档生成 `.ganttmd/`。

### P2：规则复用

- 把页面健康检查逐步迁移为复用 `src/validator.js` 的规则。

### P3：Agent 辅助命令

未来可以考虑：

```bash

```

但在真实接入跑通前，不应急着扩展 CLI 命令。

## 9. Claude 的补充与方向修正

审查者：Claude
审查时间：2026-05-23
审查角度：从「规则成本」角度对本文及后续扩展方向做一次反向校准。

### 9.1 一个根本性担忧：规则膨胀

本文目前 370 行，结构和判断都很好。但同时也暴露了一个真实风险：

> AGENTS.md / 协作规则是 Agent **每次开会话都要读**的东西。每加一条规则，Agent 上下文多一行，新 Agent 上手门槛抬一截，规则之间冲突的概率多一点。

如果以后每发现一个使用问题都通过「加规则」解决，AGENTS.md 会从几十行膨胀到几百行，最终 GanttMD 反而成为 Agent 的负担，而不是工具。

### 9.2 四个新发现的问题不应该靠加规则解决

Claude 之前提出 Codex 这份文档漏掉了四件事：

1. Agent 错误恢复路径（PR 被打回怎么办、领了任务做不了怎么退）
2. 多 Agent 并行时的冲突避免（codex 和 claude 同时领同一个任务）
3. 临时任务 / bugfix 怎么进 GanttMD
4. 人类不打开页面时怎么被动获取关键信息

经过反思，**这四个问题没有一个真正需要加协作规则**。逐项替换方案：

| 问题 | 错误方向（加规则） | 推荐方向 |
|------|--------------------|----------|
| 错误恢复 | AGENTS.md 加一节「非 happy path」 | validator 当导师：检测到 review 任务长期不动就给出修复建议；Agent 不需要事先学，触发时按提示做 |
| 多 Agent 协作 | AGENTS.md 加「领取前必须看 agent 字段」 | validator 加 1 条规则：同任务多 agent 冲突警告。如做 CLI，`ganttmd claim` 原子化就够了 |
| 临时任务 / bugfix | AGENTS.md 加「如何处理计划外工作」 | schema 微调：加 `kind: ad_hoc` 任务类型或 `bugfix` track 枚举值，配套 5 行模板 |
| 人类不开页面 | AGENTS.md 加「提交 PR 时必须附 .ganttmd 摘要」 | 工具能力：`ganttmd summary --pr` 命令输出 markdown，Agent 一键塞进 PR 描述，不需记规则 |

### 9.3 通用判断标准

任何新问题，按以下顺序问，**不到第 5 步不要写规则**：

1. **能否用 validator 拦住？** → 加 1 条检查（最便宜，规则零增加）
2. **能否用 schema 表达？** → 加 1 个字段或枚举（规则换成数据）
3. **能否用 CLI 强制？** → 加 1 个命令（把规则编译到工具里）
4. **能否靠 error message 现场教学？** → 让 validator / CLI 输出「应该怎么做」
5. **以上都不行 → 才考虑写到 AGENTS.md**

这个排序的原理：越靠前的方案，越能把"Agent 必须记住的事"转化为"工具自动处理的事"。

### 9.4 对本文档现有内容的减法建议

本文 80% 内容属于上述 1-4 类，只有 §1 六条边界是真正必须 Agent 内化的「协议」。其余部分可以重新归口：

- **§3 Agent 路径**里"领取 / 执行 / 提交"那些动作，能让 `ganttmd next` 和 `ganttmd claim` 命令自带就不必写文档
- **§5 校验路径**几乎就是 README 校验一节的复述，可考虑合并
- **§2.1 首次接入步骤**可以变成 `npx ganttmd init` 一行命令，文档只保留"为什么这样做"
- **§4 PR follow-up 模板**可以变成 `ganttmd followup --from-pr PR#27 RR-003 "..."` 命令

### 9.5 目标

**AGENTS.md 模板应控制在 50 行以内。**

Agent 读 50 行协议 + 触发问题时看 validator 提示 = 能干活。不需要读 370 行才能开始。

本文档（370 行）保留为「设计参考」是有价值的——它把所有边界都想清楚了。但它的目标读者是**设计者和主控**，不是每次开会话的 Agent。建议本文档定位调整为：

> 设计参考文档。AGENTS.md 模板和 SCHEMA 是从本文档蒸馏出来的执行规则；本文档本身不要求 Agent 阅读。

### 9.6 修正后的下一步建议

不再加任何 Agent 必读规则。改成：

   - 同任务多 agent 警告

## 10. Codex 修正：先归口，再简化 AGENTS.md

审查者：Codex
审查时间：2026-05-23
结论：同意 Claude 的方向，但执行顺序需要更谨慎。

不应马上重写或删减 `AGENTS.md`。正确顺序是：

1. 先盘点现有规则。
2. 判断每条规则最适合归口到哪里。
3. 对能下沉的规则，先补 schema、validator、CLI 或页面能力。
4. 每实现一条工具化 / schema 化替代能力，就从 `AGENTS.md` 中删除或压缩对应规则。
5. 持续重复「实现一条，删除一条」，最终自然收敛成 50 行以内的极简 Agent 协议。

不要先大规模重写 `AGENTS.md`。否则会出现一个危险窗口：文档规则被删了，但工具能力还没接住，Agent 反而更容易失控。

### 10.1 执行原则：实现一条，删除一条

规则下沉必须遵守以下闭环：

1. **选择一条规则**：从 `AGENTS.md` 或长文档中找一条可工具化规则。
2. **确定承接层**：schema、validator、CLI、页面或错误提示。
3. **实现承接能力**：例如新增字段、校验、命令或页面提示。
4. **验证承接有效**：测试、样例 validate 或页面检查通过。
5. **删除或压缩原规则**：从 Agent 必读协议中移除对应自然语言说明，只保留必要入口。
6. **记录迁移结果**：在规则归口表中标注“已下沉”。

这能保证 `AGENTS.md` 的瘦身是工程结果，而不是文档整理动作。

### 10.2 规则归口判断表

| 规则 / 问题 | 最终归口 | 原因 | 当前动作 |
| --- | --- | --- | --- |
| 任务状态只允许 `todo / in_progress / review / done / cancelled` | schema + validator | 状态枚举是结构规则，不应靠 Agent 记忆 | 已下沉：validator 已检查，Agent 模板已压缩为按 SCHEMA 写 |

### 10.3 分层后的文档定位

GanttMD 后续应形成四层，而不是把所有内容都塞进 `AGENTS.md`：

1. **设计参考层**：本文档，给产品设计者和项目主控看，解释为什么这样设计。
2. **Schema 层**：`SCHEMA.md` 和字段文档，定义可写数据结构。
3. **工具层**：validator、页面、未来 CLI，把规则变成检查或动作。
4. **Agent 协议层**：极简 `AGENTS.md`，只保留工具无法替代的行为边界。

### 10.4 下一步执行顺序

**P0：先做规则归口，不急着瘦身。**

## 12. 用户的核心原则：AGENTS.md 每一行都是高成本

讨论方：项目负责人
时间：2026-05-23
背景：在审查当前 50 行模板时提出关键判断。

### 12.1 原则

> **AGENTS.md 的每一行都非常珍贵，因为它每次都会被 Agent 读取。**
> **里面的规则一定要是对整个项目都通用的、对整个项目都至关重要的规则。**

这条原则比"压缩到 50 行"更严格。"压缩"是衡量字数，"通用且至关重要"是衡量**每一行的资格**。

### 12.2 什么内容**有资格**进 AGENTS.md

只有同时满足以下条件的内容才有资格：

1. **每次会话都需要**——不是某次操作时才查
2. **整个项目都通用**——不是某类任务或某个状态下才适用
3. **工具拦不住**——不能用 validator / schema / CLI / error message 替代
4. **不遵守就出大事**——违反了会导致项目级别的错误（凭空编造、越权关闭、跨任务污染）

### 12.3 什么内容**没有资格**进 AGENTS.md

按上述四条标准过滤，当前 50 行模板里没资格的部分包括：

| 内容 | 为什么没资格 | 应该去哪里 |
|------|--------------|------------|
| "领取任务时改 status: in_progress 补 owner" | 操作型教学，触发时学就行 | validator error 提示 / SCHEMA 示例 |
| "等待复核用 status: review" | 状态使用方法 | SCHEMA.md 状态枚举 + 含义表 |
| "真实闭环用 status: done 写 evidence" | 状态使用方法 | SCHEMA.md + validator "done 缺 evidence" 提示 |
| "明确不做用 status: cancelled 写 cancel_reason" | 状态使用方法 | SCHEMA.md + validator "cancelled 缺 cancel_reason" 提示 |
| "PR follow-up 必须有 source_pr/source_rr" | 字段约束 | validator 已经检查了 |
| "提交前跑 validate" | 这条**有资格**——它是工具拦不住的元规则 | 留在 AGENTS.md |

### 12.4 真正极简版（约 15 行）

按这套标准过滤后的 AGENTS.md 应该是：

```markdown
## 任务管理：GanttMD

### 入口
- `.ganttmd/config.yaml` / `tasks/*.md` / `followups.md`
- `.ganttmd/index.html`（人类查看）
- 字段、状态、规则以 `SCHEMA.md` 为准

### 不允许（工具拦不住的硬禁令）
- 跳过 `.ganttmd/` 自行决定下一步
- 凭空编造任务、来源文档或证据
- 修改与当前任务无关的状态
- 作为普通 Agent 关闭、删除、转换 follow-up
- 大范围重排任务文件（除非用户明确要求）

### 提交前
- 跑 `npm run validate -- .`，按错误提示修复后再提交
```

剩下的内容由 validator 错误信息 + SCHEMA.md 触发式提供给 Agent，不预先占用 context。

### 12.5 这条原则的更广含义

这条原则不只适用于 GanttMD 的 AGENTS.md 模板，也适用于使用方（如 jwxt）的 AGENTS.md：

- 每个项目的 AGENTS.md 都应该按这条原则审视
- 任何想加新规则的人都应该先问：「这条是工具拦不住的吗？是每次都要读的吗？」
- 不满足就把它放到 schema、validator 错误信息、文档查阅里

### 12.6 对 P3 任务的修正

§10.4 P3 说"最后生成 50 行以内的极简 Agent 模板"。按 §12.1 原则，这个目标应该调整为：

> **最后生成「每一行都满足通用 + 至关重要 + 工具拦不住」标准的 Agent 模板，预计 15-20 行。**

50 行不是目标，是当前的中间状态。真正的目标是「最低必需」。

### 12.7 请 Codex 执行

按 §12 原则重新审视 `docs/Agent协作规则模板.md`，每条规则按 §12.2 四条标准过一遍。不满足的全部下沉到对应位置（SCHEMA / validator / 任务字段说明）。最终产出真正"每行都有资格"的版本。

## 13. Codex 评估与执行结论

评估方：Codex
时间：2026-05-23
结论：采纳 §12 原则，并将其作为 GanttMD 的 AGENTS.md 设计上位原则。

### 13.1 修正表述

不是“工具能检查的都不能写进 AGENTS.md”，而是：

> AGENTS.md 只写工具拦不住的行为边界，以及每次进入项目都必须知道的入口。

原因：

- validator 能检查 `source_docs` 是否存在，但不能证明 Agent 执行前真的读过。
- validator 能检查 follow-up 字段，但不能知道 Agent 在总结里写了“后续再做”却没有登记。
- validator 能检查任务依赖结构，但不能阻止 Agent 跳过 `.ganttmd/` 直接按聊天上下文开工。

### 13.2 已下沉内容

以下内容不再写入极简模板：

- `status: in_progress / review / done / cancelled` 的具体用法。
- `done` 必须有 evidence。
- `cancelled` 必须有原因或 resolution。
- `in_progress` 应填写 owner / agent。
- PR follow-up 必须有 `source_pr / source_rr`。
- follow-up 不同状态的必填字段。

这些规则已经由 `SCHEMA.md`、`docs/任务字段说明.md` 和 validator 承接。

### 13.3 保留内容

以下内容继续留在 `docs/Agent协作规则模板.md`：

- GanttMD 入口。
- 工作前必须读取 `.ganttmd/`。
- 执行任务前必须读取当前任务的 `source_docs`。
- 不得凭空编造任务、来源文档、依赖或证据。
- 不得修改无关任务状态。
- 普通 Agent 不得关闭、删除、转换 follow-up。
- “后续再做 / 暂不处理 / 本轮不修”等未闭环事项必须登记到 follow-up。
- 提交前运行 validate。

这些都是工具无法完全拦截、但违反后会造成项目级错误的硬边界。

### 13.4 执行结果

`docs/Agent协作规则模板.md` 已改成“入口 + 工作边界 + 提交前”三段式极简模板。它不再承担教程功能，教程和字段细节由 schema、字段说明和 validator 触发式提供。
