# 人机协作使用路径与边界

本文档从真实使用路径出发，说明人类负责人和 AI Agent 如何共同使用 GanttMD，以及哪些边界不能混淆。

GanttMD 的定位不是通用项目管理系统，而是 AI Agent 参与开发时的任务状态层。它要解决的问题是：项目状态能被人看懂，也能被 Agent 稳定读取、更新和校验。

## 1. 核心原则

### 1.1 真相源边界

`.ganttmd/` 是任务状态真相源，只保存任务、依赖、状态、证据链、阻塞和 follow-up。

正式需求、技术设计、数据模型、接口清单、测试规范、PR 讨论和长篇方案不应搬进 GanttMD。GanttMD 只通过 `source_docs`、`source_pr`、`source_rr`、`source_commit` 引用它们。

### 1.2 写权限边界

普通 Agent 可以：

- 领取任务。
- 更新自己正在执行的任务状态。
- 补充 `evidence`、`verification`、`review_status`。
- 追加新的 open follow-up。
- 对已有 follow-up 追加补充说明或证据。

普通 Agent 不得：

- 删除任务。
- 大范围重排任务文件。
- 关闭 follow-up。
- 把 follow-up 转成正式任务。
- 把用户裁决、延期接受或取消决定写成既成事实。

项目主控可以：

- 新增、合并、拆分、取消任务。
- 清理 follow-up。
- 将 follow-up 转成正式任务。
- 接受延期并设置复核时间。
- 裁决任务是否真实完成。

### 1.3 完成态边界

`done` 不等于 Agent 口头说“完成了”。

任务进入 `done` 至少应满足：

- 有 `evidence`。
- 工程类任务有 `verification`。
- 需要复核的任务有 `review_status`。
- 如产生剩余事项，已登记到 `.ganttmd/followups.md`。

如果任务已有产出但还在等待 PR、复核或用户判断，应使用 `status: review`。

### 1.4 阻塞边界

阻塞优先由依赖派生。一个 `todo` 任务如果存在未完成前置依赖，看板可显示为被阻塞。

外部阻塞、用户裁决、资料等待和延期接受不应滥用 `status: blocked`。这些事项应通过 `blocked_reason`、follow-up 或风险项表达。

### 1.5 延期边界

“后续再做”“以后优化”“暂不处理”“本轮不修”不能只留在聊天总结或 PR 回复里。

只要这类事项会影响后续交付、验收、风险或用户判断，就必须登记到 `.ganttmd/followups.md`。

`accepted`、`deferred`、`external_wait` 等长期事项必须有 `next_review_at` 或明确触发条件，否则会变成新的沉没清单。

## 2. 人类负责人使用路径

### 2.1 首次接入

人类负责人接入一个项目时，应完成以下动作：

1. 创建 `.ganttmd/config.yaml`。
2. 创建 `.ganttmd/tasks/*.md`。
3. 创建 `.ganttmd/followups.md`。
4. 从仓库 `examples/minimal/.ganttmd/` 复制 `index.html` 与 `rules.js` 到项目的 `.ganttmd/` 目录（与 config.yaml / tasks/ 同级）。
5. 将 GanttMD 规则写入项目 `AGENTS.md`。
6. 打开页面，选择项目目录。
7. 运行校验命令：

```bash
npm run validate -- .
```

最低接入成功标准：

- 页面能读取任务。
- 里程碑能显示。
- 执行视角能看到任务队列。
- 风险视角能看到阻塞和健康检查。
- Follow-up 视角能显示清单。
- validate 没有 warning。

### 2.2 日常查看

人类负责人日常主要看 5 件事：

- 当前正在做什么。
- 下一步建议做什么。
- 哪些任务卡住了。
- 哪些事项需要用户裁决。
- 哪些 follow-up、延期项或外部等待还没清理。

默认不应要求人类负责人阅读所有字段、所有 PR 评论、所有测试输出。页面应先展示判断摘要，再允许点开追溯证据。

### 2.3 主控清理

项目主控应定期清理：

- open follow-up。
- accepted follow-up。
- 外部等待。
- 用户裁决。
- 超期未复核事项。
- 长期 in_progress 任务。
- review 状态但无复核结论的任务。

清理结果只能有几类：

- 转正式任务：写入 `.ganttmd/tasks/*.md`，follow-up 改为 `converted`。
- 继续等待：补 `next_review_at` 和原因。
- 已处理：补 `resolution`，改为 `done`。
- 明确不做：补 `resolution`，改为 `wontfix`。
- 需要用户裁决：保持 open 或 accepted，并明确 `decision_owner`。

### 2.4 判断真实完成

主控判断任务是否完成时，应先看：

- `evidence` 是否存在。
- `verification` 是否足够。
- `review_status` 是否说明复核结论。
- 是否产生未登记 follow-up。
- 下游任务是否会被本次实现方式阻塞。

如果缺关键证据，任务不应进入 `done`。可以先进入 `review`，等待补证据或复核。

## 3. Agent 使用路径

### 3.1 进入项目

Agent 开始工作前必须先读取：

1. 项目 `AGENTS.md`。
2. `.ganttmd/config.yaml`。
3. `.ganttmd/tasks/*.md`。
4. `.ganttmd/followups.md`。

如果项目提供校验脚本，应先运行：

```bash
npm run validate -- .
```

Agent 不应跳过 GanttMD 直接根据聊天上下文自行决定下一步。

### 3.2 选择任务

Agent 优先选择：

- `status: todo`。
- 所有 `dependencies` 已完成。
- `source_docs` 明确且可读取。
- `next_action` 明确。
- `acceptance` 明确。

Agent 不应领取依赖未完成、来源文档缺失、验收边界不清晰的任务。遇到这种情况，应先补字段、推进前置任务，或登记问题交给主控。

### 3.3 领取任务

领取任务时，Agent 应更新：

```yaml
status: in_progress
agent: codex
start_date: 2026-05-23
```

如果已经存在其他 `agent` 或 `owner`，应先确认是否接手、并行或冲突，不能直接覆盖。

### 3.4 执行任务

执行时，Agent 应按以下顺序推进：

1. 阅读 `source_docs`。
2. 对照 `next_action` 明确本轮工作范围。
3. 对照 `acceptance` 判断完成边界。
4. 检查 `downstream_constraints`，避免破坏下游任务。
5. 实施改动。
6. 运行必要验证。
7. 更新任务证据链。

如果执行中发现任务定义错误，应先更新 GanttMD 或向主控说明，而不是绕过任务继续做。

### 3.5 提交前

Agent 提交前应运行：

```bash
npm run validate -- .
```

如果 validate 出现 warning，优先修复 `.ganttmd/`，不能只在回复里解释。

提交说明应包含：

- 修改了哪些任务。
- 哪些任务进入 review 或 done。
- 新增了哪些 evidence。
- 是否新增 follow-up。
- 是否还有阻塞或用户裁决。

### 3.6 完成或复核

如果任务已经完成但需要复核，应写：

```yaml
status: review
review_status: pending
evidence: [PR#27]
```

如果任务真实闭环，应写：

```yaml
status: done
evidence: [PR#27, commit:abcdef]
verification: pnpm test
review_status: passed
```

如果任务不做，应写：

```yaml
status: cancelled
cancel_reason: 明确取消原因
resolution: 后续如何处理
```

## 4. PR 与 Follow-up 路径

### 4.1 PR 中产生 follow-up

PR 评论区出现以下情况时，必须登记 follow-up：

- `[REVIEW]` 提出可延后项。
- `[FIX-REPLY]` 写“后续处理”。
- `[RECHECK]` 发现还有尾项但允许合并。
- `[MERGE-READY]` 前仍有不影响合并的剩余风险。

来自 PR 的 follow-up 必须填写：

```yaml
source_type: pr_review
source_pr: PR#27
source_rr: RR-003
```

没有 `source_pr` 和 `source_rr` 的 PR follow-up 视为不可追溯。

### 4.2 Follow-up 转正式任务

只有项目主控可以把 follow-up 转成正式任务。

转换时应：

1. 在 `.ganttmd/tasks/*.md` 新增正式任务。
2. 填写任务 `source_docs` 或 PR 来源。
3. 给任务分配 `milestone`、`track`、`domain`。
4. 将 follow-up 改为 `converted`。
5. 填写 `converted_task` 和 `resolution`。

普通 Agent 只能建议转换，不能直接转换。

## 5. 校验路径

校验器的目标不是替代人判断，而是防止结构性错误进入任务真相源。

当前校验重点：

- 任务 ID 重复或缺失。
- 依赖指向不存在任务。
- 任务缺少 `milestone` 或 `track`。
- 任务引用未知里程碑。
- `source_docs` 指向不存在文档。
- `done` 缺少 `evidence`。
- 工程类 `done` 缺少 `verification`.
- `review` 缺少 `review_status`。
- PR follow-up 缺少 `source_pr` 或 `source_rr`。
- accepted follow-up 缺少主控、决策或复核时间。

后续校验器应继续补：

- 任务超过 N 天未更新。
- `in_progress` 长期无人认领或 owner 不明确。
- L2 / 高风险任务缺少复核状态。
- follow-up 超过 `next_review_at` 未处理。
- evidence 中 PR / commit 格式不规范。
- 页面健康检查和 CLI 校验结果共用同一套规则。

## 6. 当前已覆盖能力

当前 GanttMD 已具备：

- Markdown 任务真相源。
- 静态只读看板。
- 执行、里程碑、主线、模块、风险、Follow-up 视图。
- 任务依赖展示。
- Agent 指令草案。
- follow-up 类型和状态治理。
- 证据链字段。
- 命令行校验脚本。
- jwxt-lite 真实感样例。

## 7. 当前缺口

### 7.1 使用闭环缺口

- 缺少完整接入检查清单。
- 缺少主控定期清理 SOP。
- 缺少 PR 评论区到 follow-up 的具体模板。
- 缺少真实项目首次迁移步骤。

### 7.2 工具能力缺口

- 页面健康检查和 CLI 校验器规则尚未完全复用。
- CLI 还不能输出推荐任务。
- CLI 还不能自动生成接手指令。
- 页面不能直接运行本地校验脚本，只能展示内置健康检查。

### 7.3 Schema 缺口

- 任务层级、任务类型和风险等级还可以更严格。
- evidence 的格式暂时宽松。
- verification 的结构化程度不足。
- accepted / deferred / external_wait 的复核规则还可以更细。

## 8. 下一阶段优先级

### P0：真实接入闭环

- 用 jwxt 做一次真实接入。
- 从 jwxt 当前文档生成 `.ganttmd/`。
- 跑 validate。
- 记录遇到的问题到 `docs/feedback-from-jwxt.md`。

### P1：校验器增强

- 增加超期未更新检查。
- 增加 follow-up 到期检查。
- 增加 L2 / 高风险任务复核检查。
- 增加 evidence 格式检查。

### P2：规则复用

- 把页面健康检查逐步迁移为复用 `.ganttmd/validate.js` 的规则。
- 页面和 CLI 对同一份 `.ganttmd/` 给出一致结果。

### P3：Agent 辅助命令

未来可以考虑：

```bash
ganttmd next
ganttmd validate
ganttmd followups
ganttmd doctor
```

但在真实接入跑通前，不应急着扩展 CLI 命令。
