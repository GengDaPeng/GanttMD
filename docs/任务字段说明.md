# 任务字段说明

GanttMD 的任务字段不是为了写完整需求，而是为了让人和 Agent 快速判断任务是否可执行、如何接手、如何验收。

## 最小任务块

```yaml
id: S-BE-01
title: 后端工程骨架专项设计
status: todo
dependencies: []
milestone: M1
source_docs: [docs/需求说明.md]
next_action: 明确后端目录、模块边界和启动入口
acceptance: [目录结构确定, 本地启动路径明确, 后续实现任务可承接]
evidence: []
```

## 字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 稳定任务编号，不能随意改名 |
| `title` | 是 | 人类可读任务标题 |
| `status` | 是 | 只允许 `todo`、`in_progress`、`done` |
| `dependencies` | 是 | 前置任务 ID 列表 |
| `milestone` | 建议 | 所属里程碑 |
| `source_docs` | 建议 | Agent 执行前必须读取的来源文档 |
| `next_action` | 建议 | 当前任务下一步具体做什么 |
| `acceptance` | 建议 | 任务级完成边界，建议 2-4 条 |
| `evidence` | 建议 | 完成证据，如文档、提交、截图、PR |
| `agent` / `owner` | 可选 | 当前执行者 |
| `start_date` | 可选 | 开始日期 |
| `completed_date` | 可选 | 完成日期 |

## status

只允许三个源状态：

```yaml
status: todo
status: in_progress
status: done
```

`blocked` 不写入任务源数据。页面根据 `dependencies` 自动判断。

## dependencies

`dependencies` 写任务 ID：

```yaml
dependencies: [S-BE-01, S-QA-03]
```

如果依赖任务没有完成，当前任务即使写着 `todo`，页面也会显示为被阻塞。

## source_docs

`source_docs` 写 Agent 执行前必须读取的真实文档：

```yaml
source_docs: [docs/产品需求.md, docs/技术方案.md]
```

不要把任务说明本身写进 `source_docs`。它只放路径。

## next_action

`next_action` 写下一步具体动作，不写文档名。

好的写法：

```yaml
next_action: 明确后端目录、模块边界和启动入口
```

不好的写法：

```yaml
next_action: 阅读 docs/技术方案.md
```

读文档是准备动作，不是任务本身。

## acceptance

`acceptance` 是任务级完成边界，不是完整业务验收文档。

建议写 2-4 条：

```yaml
acceptance: [目录结构确定, 本地启动路径明确, 后续实现任务可承接]
```

不要把源文档里的详细验收标准全部搬进任务块。详细标准仍放在正式文档里，任务块只保留摘要边界。

## evidence

`evidence` 写完成证据：

```yaml
evidence: [docs/后端工程骨架专项设计.md, commit:abcdef]
```

如果任务完成但没有 evidence，后续 Agent 很难判断是否真的可复用。

## 任务正文

任务块外可以写补充说明：

````markdown
### S-BE-01 后端工程骨架专项设计

```ganttmd-task
...
```

补充说明写在这里。
````

正文适合写：

- 背景说明。
- 当前状态。
- 外部阻塞。
- 人类补充备注。

正文不适合写：

- 需要机器稳定解析的字段。
- 任务状态。
- 依赖列表。
