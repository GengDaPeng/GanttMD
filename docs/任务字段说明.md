# 任务字段说明

GanttMD 的任务字段不是为了写完整需求，而是为了让人和 Agent 快速判断任务是否可执行、如何接手、如何验收。

## 最小任务块

```yaml
id: S-BE-01
title: 后端工程骨架专项设计
kind: task
status: todo
dependencies: []
milestone: M1
track: backend
domain: safety_attendance
priority: P0
source_docs: [docs/需求说明.md]
next_action: 明确后端目录、模块边界和启动入口
acceptance: [目录结构确定, 本地启动路径明确, 后续实现任务可承接]
evidence: []
verification:
review_status:
updated_at: 2026-05-23
```

## 字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 稳定任务编号，不能随意改名 |
| `title` | 是 | 人类可读任务标题 |
| `kind` | 可选 | 任务类型：`task`、`bugfix`、`ad_hoc`、`review`、`harness`；未填写时按 `task` 理解 |
| `status` | 是 | 只允许 `todo`、`in_progress`、`review`、`done`、`cancelled` |
| `dependencies` | 是 | 前置任务 ID 列表 |
| `milestone` | 建议 | 所属里程碑 |
| `track` | 建议 | 工作主线，如 `spec`、`backend`、`frontend`、`infra`、`quality`、`docs`、`ops` |
| `domain` | 建议 | 业务域或能力域，如 `student`、`approval`、`safety_attendance`、`notification` |
| `priority` | 建议 | 优先级：`P0`、`P1`、`P2`、`P3` |
| `source_docs` | 建议 | 当前任务的需求、设计或证据依据文档 |
| `next_action` | 建议 | 当前任务下一步具体做什么 |
| `acceptance` | 建议 | 任务级完成边界，建议 2-4 条 |
| `evidence` | 建议 | 完成证据，如文档、提交、截图、PR |
| `verification` | 条件必填 | 代码或工程任务完成时填写测试命令、CI、手工验证或未验证原因 |
| `review_status` | 条件必填 | 复核状态：`pending`、`passed`、`must_fix`、`deferred` |
| `agent` / `owner` | 条件必填 | `in_progress` 时应填写，避免多 Agent 撞车 |
| `start_date` | 可选 | 开始日期 |
| `completed_date` | 可选 | 完成日期 |
| `closed_at` | 可选 | 终态关闭日期，适用于 done / cancelled 的统一归档判断 |
| `cancelled_at` | 可选 | 取消日期；如果已填写 closed_at，可不填 |
| `archived_at` | 可选 | 归档日期；归档后默认从活跃看板中隐藏 |
| `archived_reason` | 可选 | 归档原因，如 `done_over_7_days`、`cancelled_over_7_days` |
| `updated_at` | 建议 | 最后一次更新日期 |

## status

只允许五个源状态：

```yaml
status: todo
status: in_progress
status: review
status: done
status: cancelled
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `todo` | 已登记，未开工 |
| `in_progress` | 已有 Agent 或人承接 |
| `review` | 已有产出，等待复核、PR 或用户判断 |
| `done` | 已真实闭环，必须有 evidence |
| `cancelled` | 明确不做，必须有取消原因或 resolution |

`blocked` 默认不作为源状态写入任务。页面根据 `dependencies` 和 `blocked_reason` 自动推导阻塞展示。

如果团队确实需要显式写 `status: blocked`，必须同时填写 `blocked_reason`，否则 health check 应提示异常。

`done` 和 `cancelled` 任务不要直接删除。超过 7 天归档阈值后，validator 会提示“可归档”；项目主控可补 `archived_at` 和 `archived_reason` 归档，未来归档命令应把任务移动到历史文件，而不是永久删除。

归档不是源状态。不要把 `status` 改成 `archived`；任务仍保留 `done` 或 `cancelled`。恢复任务时删除 `archived_at` 和 `archived_reason`。

## kind

`kind` 表达任务来源或执行形态，不替代 `status`。

| kind | 含义 |
| --- | --- |
| `task` | 常规计划内任务；未填写时按 task 理解 |
| `bugfix` | 缺陷修复 |
| `ad_hoc` | 计划外临时任务 |
| `review` | 复核、审查或确认任务 |
| `harness` | 工具、脚手架、AI 工作流或测试夹具任务 |

计划外工作不要只留在聊天里。若需要进入任务治理，应登记为 `kind: ad_hoc` 或 `kind: bugfix`，并补充来源文档、原因和验收边界。

## track 和 domain

`track` 和 `domain` 必须拆开。

`track` 表达工作主线，建议先控制在少量稳定值内：

```yaml
track: spec
track: backend
track: frontend
track: infra
track: quality
track: docs
track: ops
```

`domain` 表达业务域或能力域：

```yaml
domain: safety_attendance
domain: student
domain: class
domain: teacher
domain: approval
domain: settings
domain: org_permission
domain: notification
```

例如安全到校后端 API：

```yaml
track: backend
domain: safety_attendance
```

旧字段 `module` 作为 `domain` 的兼容别名。旧主线值 `quality_gate` 作为 `quality` 的兼容别名。新任务应优先使用 `domain` 和 `quality`。

视图层建议：

- `主线视角` 按 `track` 分组，回答“规格、后端、前端、基础设施、质量、文档、运维各推进到哪里”。
- `领域视角` 按 `domain` 分组，回答“某个业务域或能力域内部哪些任务完成、阻塞或待复核”。
- 任务文件可以继续按维护便利拆分，不要求文件名等于业务域名。

## dependencies

`dependencies` 写任务 ID：

```yaml
dependencies: [S-BE-01, S-QA-03]
```

如果依赖任务没有完成，当前任务即使写着 `todo`，页面也会显示为被阻塞。

## source_docs

`source_docs` 写当前任务的需求、设计或证据依据文档：

```yaml
source_docs: [docs/产品需求.md, docs/技术方案.md]
```

不要把任务说明本身写进 `source_docs`。它只放路径或章节引用。

`source_docs` 不是第二套进度真相源。动态进度、任务状态、阻塞和 follow-up 只写在 `.ganttmd/`；`source_docs` 只说明任务依据来自哪里。

## next_action

`next_action` 写下一步具体动作，不写文档名。

好的写法：

```yaml
next_action: 明确后端目录、模块边界和启动入口
```

不好的写法：

```yaml
next_action: 阅读 docs/技术方案.md
```

读文档是准备动作，不是任务本身。

## acceptance

`acceptance` 是任务级完成边界，不是完整业务验收文档。

建议写 2-4 条：

```yaml
acceptance: [目录结构确定, 本地启动路径明确, 后续实现任务可承接]
```

不要把源文档里的详细验收标准全部搬进任务块。详细标准仍放在正式文档里，任务块只保留摘要边界。

## evidence

`evidence` 写完成证据：

```yaml
evidence: [docs/后端工程骨架专项设计.md, commit:abcdef]
```

如果任务完成但没有 evidence，后续 Agent 很难判断是否真的可复用。

`done` 任务必须有 `evidence`。不同任务类型的证据要求不同：

| 任务类型 | 必须证据 | 建议证据 |
| --- | --- | --- |
| 代码实现 | PR 或 commit | verification、review_status |
| 工程配置 | commit 或配置文件路径 | verification |
| 规格/设计文档 | 正式文档章节 | review_status |
| 调研/裁决 | decision 记录 | source_docs |

`verification` 可以写测试命令、CI、手工验证，也可以明确写未验证原因。

## 任务正文

任务块外可以写补充说明：

````markdown
### S-BE-01 后端工程骨架专项设计

```ganttmd-task
...
```

补充说明写在这里。
````

正文适合写：

- 背景说明。
- 当前状态。
- 外部阻塞。
- 人类补充备注。

正文不适合写：

- 需要机器稳定解析的字段。
- 任务状态。
- 依赖列表。
