# 本地服务与工作树实时看板方案

状态：讨论稿  
目标读者：GanttMD 开发者、项目主控、负责接入真实项目的 Agent

## 1. 背景

当前 GanttMD 的 MVP 以“静态网页 + `.ganttmd/` 静态文档”为核心：

- `.ganttmd/tasks/*.md` 是任务状态真相源。
- `.ganttmd/followups.md` 是 follow-up 和待清理事项真相源。
- `.ganttmd/index.html` 通过浏览器选择目录读取文件并渲染看板。
- `validate.js` / `src/validator.js` 负责结构校验。

这个形态足够支撑单分支、短任务、轻量接入，但在真实 AI 编程项目里会遇到明显边界：

- 任务往往被派到独立 worktree / branch 中执行。
- 一个 worktree / branch 可能连续完成一组关联任务，而不是一个任务一个分支。
- 大任务内部会有 checklist，任务是否真实完成取决于 checklist 是否全部收口。
- 人类主控在主分支看板中看不到未合并 worktree 的实时状态。
- 如果要求用户手动打开每个 worktree 里的看板，会增加路径混淆和操作成本。

因此需要评估从“静态看板”升级到“本地项目运行时”的可行性。

## 2. 设计对象

本方案设计的是 GanttMD Local Runtime，暂称：

```bash
ganttmd serve
```

它不是新的任务真相源，也不是数据库服务，而是一个本地只读优先的项目状态聚合器。

核心职责：

1. 读取当前项目 `.ganttmd/`。
2. 自动发现 Git worktree、branch、HEAD 和 dirty 状态。
3. 读取各 worktree 中的 `.ganttmd/`。
4. 汇总任务、follow-up、checklist、PR、commit、证据链。
5. 生成主看板可消费的运行时投影。
6. 通过本地 HTTP 服务提供页面和 API。

## 3. 第一性问题

要解决的问题不是“看板怎么多显示一个字段”，而是：

> 人类主控如何在一个入口里看到多 Agent、多 worktree、多分支正在推进哪些任务，以及每个任务内部是否按清单真实收口。

最低可接受结果：

- 主看板能自动识别当前项目有哪些 worktree。
- 主看板能显示每个任务当前在哪个 branch / worktree 被推进。
- 主看板能显示 worktree 内任务状态是否和主分支不同。
- 任务详情能显示 checklist 完成度和每项证据。
- 校验器能发现终态任务 checklist 未完成、worktree 状态冲突等问题。

不做的真实损失：

- 长任务几天不合并时，主控无法从主看板了解真实进展。
- worktree 内的任务状态和主分支看板脱节。
- Agent 可能在分支内口头闭环，但 checklist 或证据未完整落地。
- 多个 worktree 同时改同一任务时，主控难以及时发现冲突。

## 4. 系统不变量

无论是否引入本地服务，以下约束不能破坏：

1. `.ganttmd/` 仍是任务状态真相源。
2. 本地服务生成的是运行时投影，不替代可提交文件。
3. worktree 代理默认只写自己所在 worktree 的 `.ganttmd/`，不跨目录改主分支。
4. 主分支不应被本地服务静默改写。
5. 自动发现可以读 Git 状态，但自动写文件必须显式命令、可审查、可回滚。
6. 静态网页模式继续保留，作为无服务环境的 fallback。
7. PR / commit / verification / checklist evidence 必须可追溯。
8. 多项目应由同一个本地入口管理，不要求用户为每个项目记一个端口。

## 5. 候选方案

### 方案 A：继续静态模式，手动选择 worktree 目录

用户在页面里手动选择每个 worktree 的 `.ganttmd/` 或项目根目录。

优点：

- 不需要新增服务。
- 当前实现基本可用。

缺点：

- 操作成本高。
- 容易混淆当前看的到底是主分支还是某个 worktree。
- 无法形成跨 worktree 总览。
- 无法实时发现多个分支同时推进同一任务。

结论：只能作为 fallback，不适合作为真实项目主路径。

### 方案 B：主分支维护 `runs.md`，人工登记 worktree 派工

在主分支 `.ganttmd/runs.md` 记录：

```yaml
id: RUN-001
branch: feat/safety-attendance
worktree_label: 安全到校纵切
tasks: [S-BE-09, S-FE-02, S-QA-13]
current_task: S-FE-02
status: active
```

优点：

- 文件化、可审查。
- 不需要自动扫描。
- 能表达“任务派给哪个分支”。

缺点：

- 只能知道派工，不知道分支内实时进度。
- 仍依赖 Agent 或主控手工更新。
- 容易再次形成“说了但没落文档”的问题。

结论：可以作为显式派工记录，但不能单独解决实时监控。

### 方案 C：本地服务自动扫描 Git worktree

本地服务执行：

```bash
git worktree list --porcelain
git status --porcelain
git rev-parse --abbrev-ref HEAD
git rev-parse HEAD
```

并读取各 worktree 的 `.ganttmd/`。

优点：

- 主控只打开一个入口。
- 能看到未合并 worktree 的实时任务状态。
- 能发现任务在多个分支同时变化。
- 能把 branch、commit、dirty 状态和任务状态关联起来。

缺点：

- 需要从纯静态网页升级为本地服务。
- 需要处理权限、路径、性能和安全边界。
- 页面需要支持 API 数据源。

结论：这是最符合真实使用路径的主方案。

### 方案 D：安装 Git hook 或后台守护进程自动回写主分支

在每个 worktree 提交、切换、修改任务时自动回写主分支状态。

优点：

- 主分支文件看起来总是最新。

缺点：

- 破坏分支隔离。
- 自动写文件风险高。
- 冲突处理复杂。
- 不利于 PR 审查。

结论：不建议作为当前方案。

## 6. 推荐方案

推荐采用：

> 静态 `.ganttmd/` 真相源 + `ganttmd serve` 本地运行时投影 + 可选 `runs.md` 派工记录。

关系如下：

```text
main worktree
  .ganttmd/
    config.yaml
    tasks/*.md
    followups.md
    runs.md              # 可选：主控派工记录

feature worktree A
  .ganttmd/
    tasks/*.md           # 分支内任务进展、checklist、证据

feature worktree B
  .ganttmd/
    tasks/*.md

ganttmd serve
  git worktree list
  读取各 worktree 的 .ganttmd
  生成 runtime projection
  提供 http://localhost:<port>
```

## 7. 数据模型建议

### 7.1 Worktree 投影对象

该对象由本地服务自动生成，不要求用户手写：

```yaml
id: WT-001
path: /Users/gpp/.codex/worktrees/1baf/jwxt
branch: feat/safety-attendance
head: abc123
is_main: false
is_dirty: true
has_ganttmd: true
task_count: 8
changed_task_ids: [S-BE-09, S-FE-02]
updated_at: 2026-05-24T10:30:00-07:00
```

### 7.2 Run 派工对象

该对象可选，适合主控显式派工：

```yaml
id: RUN-001
title: 安全到校纵切联调
branch: feat/safety-attendance
worktree_path:
status: active
owner: codex
tasks: [S-BE-09, S-FE-02, S-QA-13]
current_task: S-FE-02
started_at: 2026-05-24
updated_at: 2026-05-24
note: 后端 API、前端联调、测试规范连续收口
```

建议状态：

```yaml
status: planned
status: active
status: review
status: merged
status: abandoned
```

### 7.3 Task checklist

任务内部 checklist 用于表达“这个任务内部必须逐项收口的步骤”：

```yaml
checklist:
  - id: C1
    title: 建立后端接口
    status: done
    evidence: [commit:abc123]
  - id: C2
    title: 前端完成调用
    status: in_progress
    evidence: []
  - id: C3
    title: 补充验收说明
    status: todo
```

建议状态：

```yaml
status: todo
status: in_progress
status: blocked
status: done
status: skipped
```

升级规则：

- checklist 只属于父任务内部，不参与全局依赖排序。
- 如果 checklist 项影响其他任务依赖、排期、分工、PR 或可独立验收，应升级成正式任务。
- `status: done` 的任务不应存在未完成 checklist。
- checklist 的 `blocked` 必须有 `blocker_reason`。

## 8. API 草案

本地服务最小 API：

```text
GET /api/projects
POST /api/projects
GET /api/project
GET /api/state
GET /api/worktrees
GET /api/tasks
GET /api/task/:id
GET /api/health
POST /api/refresh
```

其中 `/api/state` 返回页面主要消费的聚合投影：

```json
{
  "project": {},
  "main": {},
  "worktrees": [],
  "tasks": [],
  "followups": [],
  "runs": [],
  "health": [],
  "conflicts": []
}
```

`/api/projects` 管理本机已登记项目：

```json
{
  "projects": [
    {
      "id": "jwxt",
      "name": "教务系统",
      "root": "/Users/gpp/project/gitee/jwxt",
      "lastOpenedAt": "2026-05-24T10:30:00-07:00"
    }
  ]
}
```

MVP 阶段建议只读。任何写操作都先不做，避免把本地服务变成隐式改文件工具。

## 9. 页面行为建议

### 9.1 启动模式

页面支持两种模式：

```text
file:// 模式
  手动选择目录，读取静态文件

localhost 模式
  先进入项目选择入口，再从 /api/state?project=<id> 读取聚合状态
```

页面顶部必须显示数据源：

```text
GanttMD Local · jwxt · main + 3 worktrees · last scan 10:30
```

避免用户不知道自己看的是什么。

### 9.2 多项目入口

安装式本地服务应使用单端口承载多个项目，而不是一个项目一个端口。

推荐默认入口：

```text
http://localhost:7777
```

页面首先展示本机项目列表：

- 项目名。
- 项目根目录。
- 当前主分支。
- worktree 数量。
- 风险 / 阻塞 / follow-up 摘要。
- 最近打开时间。

选择项目后进入项目看板：

```text
http://localhost:7777/project/jwxt
```

服务端维护一个本机项目索引。第一阶段可以存放在用户目录下，例如：

```text
~/.ganttmd/projects.json
```

这个索引不是项目真相源，只是本机入口配置。删除它不会影响任何项目的 `.ganttmd/` 数据。

项目登记方式：

```bash
ganttmd project add /Users/gpp/project/gitee/jwxt
ganttmd project add /Users/gpp/project/github/GanttMD
ganttmd serve
```

也可以支持直接启动时临时加入：

```bash
ganttmd serve /Users/gpp/project/gitee/jwxt
```

如果只有一个项目，服务可以直接进入该项目看板；如果有多个项目，默认进入项目选择页。

### 9.3 Worktree 总览

新增“工作树”或“运行中”区域：

- branch
- worktree path
- HEAD 短 hash
- dirty 状态
- 关联任务数
- 当前进行中任务
- 是否存在任务冲突

### 9.4 任务卡片

任务卡片增加执行上下文信息：

```text
S-FE-02
安全到校前端页面最小闭环
状态：in_progress
执行：feat/safety-attendance
Checklist：3/7
最近证据：commit abc123
```

如果同一个任务在多个 worktree 有不同状态，应提示冲突：

```text
多分支状态冲突
main: todo
feat/a: in_progress
feat/b: review
```

### 9.5 任务详情抽屉

任务详情中新增：

- 执行上下文：在哪些 worktree 出现。
- checklist：每项状态、证据、阻塞原因。
- 分支证据：commit、PR、verification。
- 与主分支差异：字段级摘要。

## 10. 校验规则建议

新增规则分两类。

### 10.1 静态规则

适用于 `.ganttmd/` 文件本身：

- checklist status 非法。
- checklist id 在同一任务内重复。
- checklist `blocked` 缺少 `blocker_reason`。
- 任务 `done` 但 checklist 仍有未完成项。
- checklist `done` 但缺少 evidence 时给 info 提示。
- run 缺少 branch 或 tasks。
- run 引用不存在任务。

### 10.2 运行时规则

只在 `ganttmd serve` 或 `ganttmd scan` 中检查：

- 同一任务在多个 worktree 状态不一致。
- 同一任务在多个 active run 中被领取。
- worktree dirty 且任务状态进入 done / review。
- worktree 没有 `.ganttmd/`，但 branch 名或 commit 信息显示正在做 GanttMD 任务。
- branch 已合并但 run 仍是 active。
- worktree 长时间未更新。

## 11. 技术可行性

### 11.1 可复用部分

当前已有：

- `src/validator.js` 中的 `loadProject(projectRoot)`。
- `validateProject(project, options)`。
- `tools/ganttmd/rules.js` 共享规则。
- 页面中的任务渲染、依赖分析、健康检查 UI。

可行做法：

1. 抽出 `src/project-loader.js`，承接 `loadProject`、parse task、parse config、parse followup。
2. CLI validator、serve runtime、测试都复用同一个 loader。
3. `ganttmd serve` 只新增 worktree scan 和 HTTP API。
4. 页面尽量复用当前渲染逻辑，只把数据来源从 File API 切到 `/api/state`。

### 11.2 Node 实现成本

可以先不用 Express，直接使用 Node 内置模块：

- `node:http`
- `node:fs`
- `node:path`
- `node:child_process`

依赖最少，适合小项目。

### 11.3 Git worktree 扫描可行性

`git worktree list --porcelain` 输出稳定，适合机器解析。示例字段包括：

```text
worktree /path/to/repo
HEAD abc123
branch refs/heads/feature/foo
```

再对每个 worktree 执行：

```bash
git status --porcelain
git rev-parse --show-toplevel
git rev-parse --abbrev-ref HEAD
git rev-parse HEAD
```

可获得足够的运行时信息。

### 11.4 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 自动扫描路径过多 | 页面变慢 | 只扫描 `git worktree list` 返回路径，不全盘搜索 |
| worktree 不在同一仓库 | 状态混入 | 用 `git rev-parse --git-common-dir` 或 remote 判断归属 |
| 文件写入冲突 | 破坏真相源 | MVP 只读，不做自动写 |
| 页面同时支持 file 和 serve 复杂 | 实现复杂 | 先保留 file 模式，serve 模式只替换数据加载入口 |
| checklist 过度膨胀 | 任务变成长文档 | 明确升级规则，复杂项升正式任务 |
| 多分支同任务冲突难合并 | 主控判断成本高 | 先只提示冲突，不自动合并 |

结论：技术上可行，风险主要在产品边界和写入策略。MVP 应坚持只读聚合。

## 12. MVP 范围

第一阶段建议只做：

1. `ganttmd serve`
2. 自动读取当前项目 `.ganttmd/`
3. 自动扫描 `git worktree list`
4. 读取每个 worktree 的 `.ganttmd/`
5. `/api/state` 输出聚合状态
6. 页面 localhost 模式自动加载 `/api/state`
7. 任务卡片显示 branch / worktree / checklist 进度
8. checklist 静态解析和校验

不做：

- 自动写主分支 `.ganttmd/`
- 自动归档
- 自动创建 PR
- 自动创建 worktree
- 数据库
- 后台常驻守护进程
- 跨机器同步

## 13. 推荐实现步骤

### 步骤 1：抽 loader

从 `src/validator.js` 抽出：

- `resolveGanttRoot`
- `loadProject`
- `parseTask`
- `parseFollowup`
- `parseConfig`

形成：

```text
src/project-loader.js
src/validator.js
```

### 步骤 2：支持 checklist 解析和规则

扩展 parser，让任务支持 YAML 风格 checklist。

如果当前轻量 parser 难以稳定解析嵌套结构，可以先采用 fenced block 内的简化格式，或暂时把 checklist 写成独立 fenced block：

````markdown
```ganttmd-checklist
task_id: S-FE-02
id: C1
title: 建立后端接口
status: done
evidence: [commit:abc123]
```
````

需要评估是否继续维护手写 parser，还是引入 YAML 解析库。若要支持嵌套 checklist，建议引入小型 YAML parser，否则规则会越来越脆弱。

### 步骤 3：实现 worktree scanner

新增：

```text
src/worktree-scanner.js
```

输出：

```js
{
  root,
  branch,
  head,
  isDirty,
  hasGanttmd,
  project
}
```

### 步骤 4：实现 runtime aggregator

新增：

```text
src/runtime-state.js
```

职责：

- 合并 main project 和 worktree projects。
- 按任务 ID 聚合各分支状态。
- 计算 checklist 完成度。
- 生成 conflicts。
- 生成 health issues。

### 步骤 5：实现 `ganttmd serve`

新增：

```text
bin/ganttmd-serve.js
```

提供：

```bash
node bin/ganttmd-serve.js .
```

或未来：

```bash
ganttmd serve
```

### 步骤 6：页面接入 localhost 数据源

页面启动时：

1. 如果当前 URL 是 `http://localhost`，请求 `/api/state`。
2. 如果请求失败，显示错误和手动选择目录入口。
3. 如果是 `file://`，维持现有手动导入。

## 14. 开放问题

1. checklist 是直接嵌套在 `ganttmd-task` 中，还是单独 `ganttmd-checklist` block？
2. 是否接受引入 YAML parser？如果接受，任务格式可以更标准；如果不接受，嵌套结构要受限。
3. `runs.md` 是否第一阶段就做？还是先完全依赖 worktree 自动扫描？
4. 多 worktree 同一任务状态冲突时，页面只提示，还是提供“以某分支为准”的显式操作？
5. PR 信息第一阶段从任务字段读取，还是尝试调用 `gh` 自动发现？

## 15. 当前结论

可行，且值得做。

但推荐边界必须清晰：

- `.ganttmd/` 继续是唯一任务真相源。
- `ganttmd serve` 只是本地运行时聚合层。
- MVP 只读，不自动写文件。
- worktree 实时状态来自扫描，不来自主分支手工同步。
- checklist 先服务任务收口，不替代正式任务依赖。

如果这个方向成立，GanttMD 会从“静态任务看板”升级为“AI solo 项目的本地项目驾驶舱”。这更符合多 Agent、多 worktree、长任务链路的实际使用方式。

| 同任务多 worktree 状态冲突 | ❌ 完全看不出 | 没有横向对比 |
| 改完不自动刷新 | ⚠️ 只能手动按按钮 | 没有 watch |
| 大任务 checklist 收口 | ❌ 任务只有 acceptance 文本 | 没结构化 checklist |
| 派工 runs | ⚠️ 用 owner/agent 勉强表达 | 但不能跨任务关联 |

5 个痛点里 4 个是当前不能解决的硬缺口。

### 16.3 推荐收口：做 3 件事，跳过 2 件事

#### ✅ 必做 1：`serve.js` 作为 .ganttmd/ 第 4 个 canonical 文件

**形态：** 与 index.html / rules.js / validate.js 并列，使用方复制时一起带走。

**实现约束：**

- 0 npm 依赖（仅用 node:http / node:fs / node:child_process）
- 1 个文件
- 启动方式：`node .ganttmd/serve.js` → `http://localhost:7777`

**职责：**

1. `git worktree list --porcelain` 扫描所有 worktree
2. 读各 worktree 的 `.ganttmd/`，复用 validate.js 的 `loadProject`
3. 暴露 `/api/state` 返回聚合 JSON
4. `/api/state?since=<ts>` 长轮询：服务端 fs.watch `.ganttmd/`，有变化立即返回，否则挂 30 秒
5. 同任务多 worktree 状态不同 → 聚合时标 `_conflicts`

**不做：**

- 不写文件
- 不自动合并冲突
- 不调用 gh
- 不需要后台守护进程（不开就不跑）

#### ✅ 必做 2：index.html 加 localhost 模式

页面启动时判断：

- `location.origin === 'http://localhost:7777'` → 从 `/api/state` 长轮询拉数据，自动刷新
- 否则 → fallback 到 file:// 选目录模式（保留旧能力）

**用户体验变化：** Agent 改完页面 1 秒内自动更新，不用手动刷新。

#### ✅ 必做 3：checklist 用独立 block

回答 §14 Q1/Q2：**独立 block，不引入 YAML parser**。

格式：

````markdown
### S-FE-02 安全到校前端

```ganttmd-task
id: S-FE-02
status: in_progress
...
```

```ganttmd-checklist
task_id: S-FE-02
items:
  - C1 [done] 后端接口对接 | evidence: commit:abc123
  - C2 [in_progress] 前端组件
  - C3 [todo] 验收说明
```
````

- 独立 block 用 `task_id` 反向引用（和 follow-up 同样的模式）
- 一行一项：`- ID [status] 描述 | evidence: xxx`
- 继续手写 parser
- rules.js 加 1 条规则：`done` 任务的 checklist 不能有未完成项 → warn

#### ❌ 不做 1：runs.md

worktree scan + 聚合已经能回答「这个 worktree 在推进哪些任务」（按 worktree 内 in_progress 任务列出来）。runs.md 是冗余表达。等 scan 不够时再说。

#### ❌ 不做 2：YAML parser

回答 §14 Q2：**不引入**。手写 parser 够用。独立 checklist block 的扁平格式不需要嵌套结构。

## 17. 最终收口：安装式、本机多项目入口与 runs.md

审查者：Codex
收口时间：2026-05-24
收口依据：项目主控明确要求“AI solo 开发节奏很快，能一步到位就一步到位”，不希望为了短期复制式目标做会导致后续重构的妥协设计。

本节作为当前最终方案，覆盖 §16 中关于“复制 `serve.js` 到 `.ganttmd/`、第一阶段不做 `runs.md`、把 scanner/runtime/server 合成单文件”的短期收口。

### 17.1 最终产品形态

GanttMD 下一阶段应直接转向安装式：

```text
GanttMD = 安装式 CLI + 项目内 .ganttmd 数据目录 + 本地服务看板
```

命令形态：

```bash
ganttmd init
ganttmd validate
ganttmd serve
ganttmd doctor
ganttmd migrate
ganttmd project add /path/to/project
```

项目里长期只保留数据：

```text
your-project/
  AGENTS.md
  .ganttmd/
    config.yaml
    tasks/
      main.md
    followups.md
    runs.md
```

不再把 `index.html`、`rules.js`、`validate.js`、`serve.js` 作为使用方项目必须复制和长期维护的程序文件。

### 17.2 为什么放弃复制式作为主线

复制式适合 MVP 验证，但不适合作为本地服务阶段的主架构。

| 问题 | 复制式后果 | 安装式处理 |
| --- | --- | --- |
| 工具升级 | 每个项目都要重新复制 JS 文件 | 升级 GanttMD 工具即可 |
| 版本漂移 | 不同项目里的 `index/rules/validate/serve` 容易不一致 | 工具代码只有一份 |
| 项目目录污染 | `.ganttmd/` 同时放数据和程序 | `.ganttmd/` 只放项目状态数据 |
| 本地服务复杂度 | `serve.js` 会变成复制到各项目的大程序 | `ganttmd serve` 由安装包提供 |
| CI 语义 | 不清楚使用哪个 validator 版本 | `ganttmd validate` 或固定包版本 |

复制式可以保留为 fallback / export 能力，而不是主路径：

```bash
ganttmd static
```

生成临时静态产物，例如：

```text
.ganttmd-dist/
  index.html
```

该目录建议加入 `.gitignore`，不作为项目真相源。

### 17.3 安装、更新、卸载边界

安装式必须区分“工具本体”和“项目数据”。

工具本体：

```bash
npm install -g ganttmd
ganttmd --version
npm update -g ganttmd
npm uninstall -g ganttmd
```

项目数据：

```bash
ganttmd init
ganttmd validate
ganttmd doctor
ganttmd migrate
```

卸载工具不会删除项目里的 `.ganttmd/`。项目数据仍随项目 Git 保留。

`config.yaml` 应增加 schema 版本：

```yaml
ganttmd:
  schema_version: 1
project:
  id: jwxt
  name: 教务系统
```

工具更新和项目数据迁移必须分开：

- `npm update -g ganttmd` 只更新工具。
- `ganttmd doctor` 检查项目 schema 是否落后。
- `ganttmd migrate` 默认 dry-run。
- `ganttmd migrate --apply` 才允许写项目文件。

更新工具绝不能自动清理、覆盖或重写项目里的运行数据。只要项目已经存在 `.ganttmd/`，`ganttmd init` 也不得覆盖已有文件，只能提示“已存在”或补齐缺失文件。任何可能改动既有任务、follow-up、run、checklist 的行为，都必须走 `migrate` 或专门显式命令，并且默认 dry-run。

迁移安全要求：

- 迁移前必须生成变更计划，列出将新增、修改、移动、删除的文件和字段。
- 默认只输出计划，不写文件。
- `--apply` 前必须确认目标文件当前内容和 dry-run 时一致，避免覆盖用户刚刚改过的数据。
- 写入前必须生成备份，例如 `.ganttmd/.backup/2026-05-24T103000/`。
- 删除类迁移默认不物理删除，优先移动到备份或 archive。
- 无法无损迁移时必须停止并提示人工处理，不能猜测。
- 迁移完成后自动运行 `ganttmd validate` 和 `ganttmd doctor`。

schema 升级规则：

```text
工具版本更新
  不改项目数据

ganttmd doctor
  发现 schema_version 落后并提示 migrate

ganttmd migrate
  输出 dry-run diff 和风险说明

ganttmd migrate --apply
  备份 -> 写入 -> validate -> doctor
```

示例：

```bash
npm update -g ganttmd
cd /path/to/project
ganttmd doctor
ganttmd migrate
ganttmd migrate --apply
```

### 17.4 单端口多项目入口

本地服务不采用“一个项目一个端口”。用户同时开发多个项目时，应只打开一个 GanttMD Local 入口。

默认入口：

```text
http://localhost:7777
```

本机项目索引：

```text
~/.ganttmd/projects.json
```

项目登记：

```bash
ganttmd project add /Users/gpp/project/gitee/jwxt
ganttmd project add /Users/gpp/project/github/GanttMD
ganttmd serve
```

页面启动后先显示项目列表：

- 项目名。
- 项目路径。
- 当前主分支。
- worktree 数量。
- 当前阻塞、风险、follow-up 摘要。
- 最近打开时间。

选择项目后进入项目看板：

```text
http://localhost:7777/project/jwxt
```

`~/.ganttmd/projects.json` 只是本机入口配置，不是项目任务真相源。删除它不会影响任何项目的 `.ganttmd/`。

### 17.5 `runs.md` 直接纳入第一阶段

`worktree scan` 和 `runs.md` 表达的是两个不同事实：

- `worktree scan`：现场事实，回答“现在各 worktree 里发生了什么”。
- `runs.md`：主控计划，回答“哪些任务被作为一个执行批次派给哪个分支/代理”。

因此 `runs.md` 不是冗余能力，应直接纳入第一阶段。

最小格式：

```yaml
id: RUN-001
title: 安全到校纵切联调
status: active
branch: feat/safety-attendance
worktree_path:
owner: codex
tasks: [S-BE-09, S-FE-02, S-QA-13]
current_task: S-FE-02
started_at: 2026-05-24
updated_at: 2026-05-24
note: 后端 API、前端联调、测试规范连续收口
```

建议状态：

```yaml
status: planned
status: active
status: review
status: merged
status: abandoned
```

基础规则：

- `active` run 必须有 `branch`、`owner`、`tasks`。
- `tasks` 必须引用存在任务。
- 同一个未完成任务不应同时出现在多个 `active` run 中。
- `current_task` 必须属于 `tasks`。
- branch 已合并但 run 仍为 `active` 时给出提示。
- worktree scan 未发现对应 branch 时给出提示，但不直接判定非法。

### 17.6 checklist 直接纳入第一阶段

大任务内部需要结构化 checklist。它不是全局任务依赖，而是父任务内部的收口清单。

采用独立 fenced block，不引入 YAML parser：

````markdown
```ganttmd-checklist
task_id: S-FE-02
items:
  - C1 [done] 后端接口对接 | evidence: commit:abc123
  - C2 [in_progress] 前端组件
  - C3 [todo] 验收说明
```
````

基础规则：

- `task_id` 必须引用存在任务。
- 同一任务内 checklist item id 不能重复。
- item status 只允许 `todo`、`in_progress`、`blocked`、`done`、`skipped`。
- `blocked` item 必须写 `blocker_reason` 或在行内说明阻塞原因。
- 父任务 `done` 时 checklist 不能有未完成项。
- checklist item 如果影响全局依赖、排期、分工、PR 或可独立验收，应升级为正式任务。

### 17.7 源码结构

不采用单文件 `serve.js`。小项目也应保持清晰边界，避免后续为扩展 worktree、runs、watch、API 和 UI 时被迫重构。

推荐结构：

```text
bin/
  ganttmd.js              # CLI 入口
src/
  project-loader.js       # 读取 config/tasks/followups/runs/checklist
  rules.js                # 共享静态规则
  validator.js            # validate 命令
  worktree-scanner.js     # git worktree / branch / dirty / head 扫描
  runtime-state.js        # 聚合项目、runs、worktrees、conflicts、health
  project-registry.js     # ~/.ganttmd/projects.json 读写
  server.js               # HTTP 服务、API、静态页面
web/
  index.html              # serve 模式页面
```

`tools/ganttmd/index.html` 可以逐步迁移到 `web/index.html`，作为安装式 `ganttmd serve` 的页面资产。

### 17.8 命令范围

第一阶段必须做：

```bash
ganttmd init
ganttmd validate
ganttmd serve
ganttmd doctor
ganttmd project add
ganttmd project list
```

第一阶段可只做 dry-run 或保留接口：

```bash
ganttmd migrate
ganttmd static
```

第一阶段不做：

- 自动写任务状态。
- 自动 claim。
- 自动 archive。
- 自动创建 PR。
- 自动创建 worktree。
- 自动合并多分支冲突。
- 自动调用 `gh` 推断 PR。

这些能力可以后续通过显式命令增加，不能混进 `serve` 的只读聚合职责。

### 17.9 API 收口

本地服务 API 以单端口多项目为前提：

```text
GET  /api/projects
POST /api/projects
GET  /api/state?project=<id>
POST /api/refresh?project=<id>
GET  /api/worktrees?project=<id>
GET  /api/tasks?project=<id>
GET  /api/task/:id?project=<id>
GET  /api/health?project=<id>
```

`/api/state` 返回：

```json
{
  "project": {},
  "source": {
    "projectId": "jwxt",
    "root": "/Users/gpp/project/gitee/jwxt",
    "servedAt": "2026-05-24T10:30:00-07:00"
  },
  "main": {},
  "worktrees": [],
  "runs": [],
  "tasks": [],
  "followups": [],
  "checklists": [],
  "health": [],
  "conflicts": []
}
```

自动刷新策略：

- 优先使用 `fs.watch` 监听已登记项目的 `.ganttmd/`。
- `fs.watch` 不可靠或不可用时降级为 5 秒轮询。
- 不引入 `chokidar`，保持 0 运行时依赖。

### 17.10 最终实现顺序

1. 改包结构和 CLI 入口：`bin/ganttmd.js`、`package.json bin`。
2. 抽 `project-loader.js`，让 validate、server、测试共用读取逻辑。
3. 迁移 `rules.js` 到 `src/rules.js`，保留必要兼容出口。
4. 增加 runs 解析、校验和样例。
5. 增加 checklist 解析、校验和样例。
6. 增加 project registry：`ganttmd project add/list`。
7. 增加 worktree scanner。
8. 增加 runtime-state 聚合层。
9. 增加 `ganttmd serve` 和单端口多项目 API。
10. 改页面为项目选择入口 + 项目看板。
11. 更新 README、使用方文档、Agent 模板和迁移说明。
12. 跑完整测试：`npm test`、`ganttmd validate`、`ganttmd serve` 本地验证。

### 17.11 当前最终结论

本阶段不再围绕复制式 MVP 继续演进。最终方案是：

> 工具安装在项目外，项目只保留 `.ganttmd/` 数据；一个本地服务入口管理多个项目；`runs.md` 表达主控派工计划；worktree scan 表达现场事实；checklist 表达大任务内部收口；serve 只读聚合，不自动写文件。

这比 §16 的短期方案实现量更大，但避免了后续从复制式单文件服务再重构到安装式模块化架构的返工。

### 18.9 更新和 schema 迁移安全补充

安装式以后，必须把“更新工具”和“迁移项目数据”彻底分开。

`npm update -g ganttmd` 或未来任何工具升级，都不得自动修改项目里的 `.ganttmd/` 数据。项目内已经运行的数据，包括任务、follow-up、runs、checklists、证据链和历史归档，都不能因为工具更新被清理、覆盖或重排。

当工具支持的新 schema 高于项目 `config.yaml` 中的 `ganttmd.schema_version` 时，只允许：

1. `ganttmd doctor` 提示 schema 落后。
2. `ganttmd migrate` 输出 dry-run 计划。
3. `ganttmd migrate --apply` 在备份后显式执行。

迁移命令必须满足：

- 不带 `--apply` 永远不写文件。
- 写入前生成 `.ganttmd/.backup/<timestamp>/`。
- 写入前校验文件未在 dry-run 后被其他进程修改。
- 对删除或拆分文件的操作，默认移动到备份或 archive，不直接丢弃。
- 遇到无法无损判断的字段或格式，停止并要求人工处理。
- 写入后自动运行 validate 和 doctor。

因此，“一次到位”指命令体系、数据模型、安装式架构和核心闭环一次成型；不代表工具可以在升级时静默改用户数据。所有会写项目文件的行为，都必须有 dry-run、明确 diff、备份和 `--apply`。
