# 安装、更新、卸载与迁移

本文面向使用 GanttMD 的项目。目标是让项目只保存 `.ganttmd/` 数据，工具本身通过安装式 CLI 提供。

## 基本边界

- 项目数据只在使用方项目的 `.ganttmd/` 中。
- `ganttmd` 工具安装在项目外。
- 更新或卸载工具不应删除、覆盖或迁移项目里的 `.ganttmd/`。
- 会写项目文件的命令必须显式执行，例如 `ganttmd init`、`ganttmd upgrade --apply`、`ganttmd migrate --apply`。
- 本地看板 `ganttmd start` 是只读聚合，不直接改任务文件。

## 安装

本仓库本地开发时：

```bash
cd /path/to/GanttMD
npm install -g .
```

发布到 npm 后：

```bash
npm install -g ganttmd
```

安装后确认：

```bash
ganttmd --version
ganttmd --help
```

如果要先确认本仓库当前状态，再把 CLI 装到全局，建议加一步：

```bash
cd /path/to/GanttMD
npm test
```

## 初始化项目

在目标项目根目录执行：

```bash
ganttmd init
```

当前初始化只补最小骨架，不覆盖已有文件，会创建：

- `.ganttmd/README.md`
- `.ganttmd/config.yaml`
- `.ganttmd/tasks/main.md`
- `.ganttmd/followups.md`
- `.ganttmd/runs.md`

其中 `tasks/main.md` 只放一个占位样例任务，用来提醒你把项目真实任务落到正式任务文件里。初始化后建议立刻执行：

```bash
ganttmd doctor
ganttmd validate
```

如果准备接入本机看板，再执行：

```bash
ganttmd project add . --id <project-id> --name <project-name>
ganttmd start --no-open
```

`start` 默认会尝试自动打开浏览器；在 CI、远程 shell 或你只想先确认服务状态时，用 `--no-open` 更稳妥。

## 更新

本仓库本地开发时：

```bash
cd /path/to/GanttMD
git pull
npm install -g .
```

发布到 npm 后：

```bash
npm update -g ganttmd
```

更新只替换本机安装的 `ganttmd` 工具，不会自动改使用方项目里的 `.ganttmd/`。

### 推荐升级入口

对普通使用方项目，优先使用：

```bash
ganttmd upgrade
```

它会做 dry-run，汇总四类结果：

- `created`：缺失但可安全补齐的托管文件
- `modified`：可确定的安全修改，例如补 `schema_version`、升级托管 `.ganttmd/README.md`
- `removed`：命中废弃白名单且内容仍是旧样板的文件
- `warnings`：命中废弃白名单，但内容看起来已被用户修改，因此跳过自动删除

当前废弃白名单示例：

- `.ganttmd/.task-card.md`
- `.ganttmd/milestones/overview.md`
- `.ganttmd/views/timeline.json`

确认输出后再执行：

```bash
ganttmd upgrade --apply
```

`upgrade --apply` 会先把改动前文件备份到 `.ganttmd/.backup/<timestamp>/upgrade/`，再进行写入或删除。

### 无缝升级承诺

- `ganttmd validate`、`ganttmd doctor`、`ganttmd status`、`ganttmd start/stop` 只读取项目数据，不会写 `.ganttmd/`。
- `ganttmd upgrade` 默认是 dry-run，不写文件。
- `ganttmd migrate` 默认是 dry-run，不写文件。
- `ganttmd migrate --apply` 目前仅会处理 `ganttmd.schema_version` 的补齐，不会改写任务的 `status`、`tasks`、`followups`、`runs`。
- `ganttmd upgrade --apply` 会先备份再修改；命中废弃白名单但内容已被用户改过的旧文件只报 warning，不自动删除。
- 所有写项目文件的命令都会写入 `.ganttmd/.backup/<timestamp>/` 备份；可据备份回滚。
- 因此这次升级本身对用户已提交的任务状态不构成「替换式」改写，最可能变化的是新增告警和新增 schema 字段。

你可以用这段流程做无缝升级核验（每个项目都可直接跑）：

```bash
# 1) 锁定基线（先记录现状）
cd /path/to/your-project
mkdir -p .ganttmd/.upgrade-check
find .ganttmd -type f \( -name '*.md' -o -name 'config.yaml' \) -print0 \
  | sort -z | xargs -0 sha256sum > .ganttmd/.upgrade-check/pre.hash

# 2) 只做检查，不落盘
ganttmd upgrade --json

# 3) 执行必要升级
ganttmd upgrade --apply

# 4) 再做一次 hash，对比除 .backup 外文件变化
find .ganttmd -type f \( -name '*.md' -o -name 'config.yaml' \) -not -path './.ganttmd/.backup/*' -print0 \
  | sort -z | xargs -0 sha256sum > .ganttmd/.upgrade-check/post.hash
diff .ganttmd/.upgrade-check/pre.hash .ganttmd/.upgrade-check/post.hash 
```

正常升级场景下，`diff` 里可能看到 `.ganttmd/README.md` 的托管说明更新、`config.yaml` 的 `ganttmd.schema_version` 增加，或已废弃且未被用户改动的旧文件被删除；任务记录正文不应变化。

更新后可能发生变化的是校验结果：新版本可能新增 warning，用来暴露以前没有拦住的结构问题。warning 不会自动改数据，但如果项目 CI 使用 `ganttmd validate`，新增 warning 会让命令退出码变为 `1`。

更新工具后，对每个使用方项目执行：

```bash
cd /path/to/your-project
ganttmd doctor
ganttmd upgrade
ganttmd validate
```

如果只是想确认“升级会不会动到任务数据”，先看 `upgrade` 的 dry-run 输出即可。

当前 `upgrade` 的自动删除只针对命中废弃白名单且内容仍是旧样板的文件。只要文件内容被用户改过，就不会自动删除，而是保留原文件并报 warning。

如果升级后出现 `review_status` 相关 warning，按下面规则处理：

- PR requested changes 和返工意见保留在 PR review 或评论中，不写入 `review_status`。
- 默认配置只允许 `pending`、`passed`、`deferred`；如团队确实要继续使用 `must_fix`，需要在 `.ganttmd/config.yaml` 显式配置 `ganttmd.review_statuses`。
- `status: review` 不能配 `review_status: passed`；通过后应改为 `status: done`。
- `status: done` 不强制填写 `review_status`；如果填写，只能是 `passed`。

如果 `ganttmd doctor` 提示 schema 落后，先运行 dry-run：

```bash
ganttmd upgrade
```

确认计划无误后再显式写入：

```bash
ganttmd upgrade --apply
ganttmd doctor
ganttmd validate
```

`upgrade --apply` 会在 `.ganttmd/.backup/` 下保存被改文件的备份。
建议把 `.ganttmd/.backup/` 加入使用方项目的 `.gitignore`，迁移备份用于本地回滚，不应提交到 Git。

## 卸载

卸载工具前可以先停止本地服务：

```bash
ganttmd stop
```

本地开发安装版：

```bash
npm uninstall -g ganttmd
```

如果是从本仓库 `npm install -g .` 安装，npm 仍按 package 名称卸载：

```bash
npm uninstall -g ganttmd
```

卸载不会删除使用方项目中的 `.ganttmd/`。如果只是从本机看板移除项目登记，不删除项目数据：

```bash
ganttmd project remove <project-id-or-path>
```

## 迁移到项目

建议按这个顺序：

1. 在 GanttMD 项目里确认样例数据和工具能力已经通过测试。
2. 在目标项目根目录创建或复制 `.ganttmd/` 数据。
3. 如项目使用 AI Agent，把 `docs/Agent协作规则模板.md` 的必要规则合并到目标项目 `AGENTS.md`。
4. 在目标项目根目录运行：

```bash
ganttmd doctor
ganttmd upgrade
ganttmd validate
```

5. 若 `upgrade` 有计划，先审查 diff，再执行：

```bash
ganttmd upgrade --apply
ganttmd doctor
ganttmd validate
```

6. 登记并打开本地看板：

```bash
ganttmd project add . --id <project-id> --name <project-name>
ganttmd start --no-open
```

7. 在页面确认：

- 项目标题、里程碑、任务数正确。
- 执行视角默认打开。
- 可执行、进行中、阻塞、已完成、已取消、已归档筛选可用。
- 任务抽屉能显示任务卡、来源文档、证据与治理、任务清单。
- 分支领取任务后，运行态能显示分支、run 和 checklist。
- Follow-up 视图能展示 open、accepted、converted 等状态。
- 风险视角和协作健康检查没有结构性 warning。

## 项目接入前检查

迁入目标项目前，至少跑：

```bash
npm test
ganttmd validate .
ganttmd doctor .
```

在目标项目中，至少跑：

```bash
ganttmd doctor
ganttmd upgrade
ganttmd validate
```

如果要接入 CI，使用方项目可以先只加：

```yaml
- name: Validate GanttMD
  run: ganttmd validate
```

## 回滚

工具更新回滚：

```bash
npm install -g ganttmd@<version>
```

如果你是从本仓库 `npm install -g .` 安装的本地开发版，回滚方式是切回目标版本后重新安装：

```bash
cd /path/to/GanttMD
git checkout <tag-or-commit>
npm install -g .
```

项目数据迁移回滚：

1. 找到 `.ganttmd/.backup/<timestamp>/`。
2. 对照备份文件和当前文件。
3. 手动恢复需要回滚的文件。
4. 运行：

```bash
ganttmd doctor
ganttmd validate
```

不要直接删除 `.ganttmd/` 来回滚；它是任务状态真相源。
