# GanttMD V4 视图系统方案讨论稿

设计强度：L2 标准。  
文档状态：讨论稿，供 Codex / Claude / 用户继续对抗讨论。  
基准版本：V3 已具备执行视角、里程碑视角、模块视角、Follow-up 视角、任务诊断、依赖抽屉和健康检查。

## 1. 背景

V3 目前把视图写成固定 tab：

- 执行视角
- 里程碑视角
- 模块视角
- Follow-up

这几个视角能支撑 MVP，但不应该成为 GanttMD 对所有软件项目的固定分类。

不同项目的真实观察方式会变化：

- 业务系统关注模块、里程碑、风险、审计。
- SaaS 产品关注客户价值、版本发布、跨团队依赖。
- AI Agent 项目关注可领取任务、上下文缺口、工具权限、虚假闭环。
- 数据项目关注数据血缘、重跑、口径、质量检查。
- 开源项目关注 issue、PR、review、release、贡献者。

因此 V4 的核心目标不是新增更多固定 tab，而是引入一层可配置的“视图系统”。

## 2. 核心命题

GanttMD 的任务真相源仍然是 `.ganttmd/modules/*.md` 和 `.ganttmd/followups.md`。

V4 要新增的是：

> 同一份 Markdown 状态数据，可以被配置成多种面向不同角色、不同决策场景的只读视图。

也就是说：

- 任务数据不因为视图增加而复制。
- 视图只描述如何过滤、分组、排序和展示字段。
- Agent 和人看到的是同一份项目状态的不同投影。

## 3. 要解决的问题

### 3.1 现在的问题

当前 V3 存在几个隐性限制：

1. 视图类型被写死在 HTML 里。
2. 新增“待讨论”“审查尾项”“Agent 视角”“风险视角”都需要改代码。
3. 不同项目不能按自身工作流选择默认视图。
4. Agent 无法从配置里理解“这个项目主控最关心哪些观察角度”。
5. 人看到的视图和 Agent 的任务选择逻辑还没有完全统一。

### 3.2 V4 的最低结果

V4 至少要做到：

1. 默认内置视图仍然开箱可用。
2. 项目可以在配置里声明额外视图。
3. 视图可以基于任务字段、状态、模块、里程碑、Agent、Follow-up、Discussion 做过滤和分组。
4. 页面只读渲染这些视图，不改 Markdown 真相源。
5. Agent 能读懂视图配置，并据此知道“主控希望我优先看什么”。

## 4. 系统不变量

无论 V4 怎么设计，不能破坏这些约束：

1. Markdown 仍是唯一真相源。
2. 可视化页面只读，不直接写回任务文件。
3. `modules/*.md` 只存正式任务，不被 follow-up 和讨论污染。
4. Follow-up 和待讨论事项是任务治理入口，不等于正式任务。
5. 普通 Agent 可以登记问题，但只有项目主控可以关闭、合并、转正式任务。
6. 视图不能制造新事实，只能投影已有事实。
7. 任何非法数据不能静默消失，必须进入健康检查或 invalid 分组。

## 5. 方案选项

### 方案 A：继续硬编码更多 tab

做法：

- 在 HTML 里继续增加 `风险视角`、`Agent视角`、`待讨论`、`审查视角`。

优点：

- 实现最快。
- 对当前样例改动最小。
- UI 行为容易控制。

缺点：

- 很快变成一个越来越长的 tab 列表。
- 每新增一种管理方式都要改代码。
- 不同项目无法按自身情况裁剪。
- 视图规则无法被 Agent 稳定读取和复用。

判断：

不推荐作为 V4 主方向。可以作为临时验证方式，但不适合继续演进。

### 方案 B：在 `config.yaml` 中定义 `views`

做法：

在 `.ganttmd/config.yaml` 增加视图声明：

```yaml
views:
  - id: execution
    name: 执行视角
    source: tasks
    filter:
      status: [todo, in_progress, done]
    group_by: execution_state
    sort_by: recommended
    fields: [id, title, status, module, milestone, owner, deps, followups]

  - id: risk
    name: 风险视角
    source: mixed
    include:
      tasks:
        effective_status: [blocked]
      followups:
        status: [open, accepted]
      discussions:
        status: [open]
    group_by: risk_type
    sort_by: severity
```

优点：

- 视图成为项目配置的一部分。
- 页面可以按配置动态渲染。
- Agent 可以读取配置，理解项目主控的观察方式。
- 不同项目可以拥有不同视图，不需要改页面代码。

缺点：

- 配置 schema 会变复杂。
- 需要定义一套有限但清晰的 `filter / group_by / sort_by / fields` 语义。
- MVP 不能一上来支持任意表达式，否则会过度设计。

判断：

推荐作为 V4 主方案。它符合 GanttMD 的轻量定位，也能自然承接后续扩展。

### 方案 C：每个视图一个 Markdown 文件

做法：

新增：

```text
.ganttmd/views/
  execution.md
  risk.md
  agent.md
  review.md
```

每个文件描述一个视图。

优点：

- Markdown 原生，Agent 容易追加和讨论。
- 每个视图可以有说明、规则和用途。
- 适合复杂项目把视图配置拆开管理。

缺点：

- 文件数量增加。
- 初期比 `config.yaml` 更重。
- 视图规则可能变得不够结构化，前端解析更麻烦。

判断：

可以作为后续扩展。V4 不建议先上，除非项目视图配置明显变长。

## 6. 推荐方案

V4 推荐采用“内置默认视图 + `config.yaml.views` 可配置视图”的混合方案。

### 6.1 默认内置视图

即使项目没有配置 `views`，页面仍提供默认视图：

1. `execution`：执行视角。
2. `milestone`：里程碑视角。
3. `module`：模块视角。
4. `followup`：Follow-up 视角。
5. `health`：健康检查视角，可以先作为右侧卡片，后续独立。

### 6.2 可配置视图

项目可以在 `config.yaml` 里声明额外视图。

V4 第一阶段只支持有限能力：

```yaml
views:
  - id: agent
    name: Agent 视角
    source: tasks
    group_by: agent
    sort_by: effective_status
    fields: [id, title, status, milestone, next_action]

  - id: risk
    name: 风险视角
    source: mixed
    include:
      tasks:
        effective_status: [blocked]
      followups:
        status: [open, accepted]
      discussions:
        status: [open]
    group_by: item_type
    sort_by: severity
```

不支持：

- 任意 JS 表达式。
- 任意嵌套查询语言。
- 前端写回 Markdown。
- 视图内直接创建任务。

## 7. 视图对象模型

V4 可以把页面展示对象抽象成 `view item`。

```text
Task        -> view item
Follow-up   -> view item
Discussion  -> view item
HealthIssue -> view item
```

统一字段：

| 字段 | 说明 |
| --- | --- |
| `item_type` | task / followup / discussion / health_issue |
| `id` | 对象 ID |
| `title` | 标题 |
| `status` | 原始状态 |
| `display_status` | 展示状态，例如 blocked / invalid |
| `source` | 来源文件或来源对象 |
| `severity` | 风险等级，可为空 |
| `milestone` | 所属里程碑，可为空 |
| `module` | 所属模块，可为空 |
| `owner` | 负责人或主控，可为空 |
| `next_review_at` | 下次复核时间，可为空 |

这样风险视角可以同时展示任务阻塞、follow-up 堆积和待讨论事项，而不需要把它们混成同一种数据。

## 8. 建议新增：待讨论清单

Follow-up 解决的是“已经决定进入跟踪的后续事项”。

待讨论清单解决的是“还没形成任务或 follow-up，需要主控或用户裁决的问题”。

建议 V4 同步定义：

```text
.ganttmd/discussions.md
```

fenced block：

````markdown
### DISC-001 是否引入项目级 views 配置

```ganttmd-discussion
id: DISC-001
title: 是否引入项目级 views 配置
status: open
source_type: user
source_task:
created_by: codex
created_at: 2026-05-22
question: GanttMD 是否应该从固定 tab 演进为可配置视图系统
options: [继续硬编码 tab, config.yaml views, views/*.md]
recommendation: config.yaml views
decision:
decided_by:
decided_at:
converted_task:
```
````

状态：

- `open`：待讨论。
- `decided`：已形成决策，但不一定转任务。
- `converted`：已转正式任务。
- `closed`：关闭，不处理。

权限：

- 所有 Agent 可追加 `open` discussion。
- 只有项目主控或用户可以写 `decision`、关闭或转任务。

注意：

Discussion 不等于 Follow-up。

- Discussion 是问题和分歧。
- Follow-up 是后续事项。
- Task 是正式执行项。

## 9. V4 默认视图建议

V4 不建议把所有视图都塞进顶部 tab。建议分成两层：

### 9.1 主视图

默认展示最常用的 4 个：

1. 执行
2. 里程碑
3. 模块
4. 风险

### 9.2 管理视图

放进一个“治理”或“更多”入口：

1. Follow-up
2. 待讨论
3. Agent
4. 审查
5. 健康检查

理由：

- 人每天最常看的是“现在做什么”和“哪里卡住”。
- Follow-up 和 Discussion 重要，但属于治理清理，不一定每次打开都要占据主导航。
- Agent 视角和审查视角更像专项入口。

## 10. Agent 协作影响

V4 后，Agent 的工作前读取顺序建议变成：

1. `AGENTS.md`
2. `.ganttmd/config.yaml`
3. `.ganttmd/config.yaml` 中的 `views`
4. `.ganttmd/modules/*.md`
5. `.ganttmd/followups.md`
6. `.ganttmd/discussions.md`

Agent 应理解：

- `execution` 视图用于判断下一步任务。
- `risk` 视图用于判断阻塞、follow-up 和讨论堆积。
- `agent` 视图用于判断自己是否已有任务占用。
- `review` 视图用于处理 PR 审查尾项。

但 Agent 领取任务时仍然只能以 `modules/*.md` 的正式任务为准。

## 11. V4 阶段切分

### 必须做

1. 在 `SCHEMA.md` 增加 `views` 配置草案。
2. 在 V4 页面中把现有 tab 改成由视图定义驱动。
3. 保留默认内置视图，保证旧 `.ganttmd/` 不配置 views 也能打开。
4. 增加 `risk` 视图，聚合 blocked task、open/accepted follow-up、open discussion。
5. 增加 `.ganttmd/discussions.md` 的 schema 和样例。

### 建议做

1. 增加 `agent` 视图。
2. 增加 `review` 视图，按 `source_pr / source_rr` 展示 PR 尾项。
3. 健康检查增加 view schema 校验。
4. 在 `Agent协作规则模板.md` 中补充视图读取规则。

### 可以延后

1. 任意自定义查询表达式。
2. 拖拽排序。
3. 页面内编辑 Markdown。
4. CLI validate。
5. 复杂甘特图和日历视图。

### 明确不做

1. 不引入数据库。
2. 不把视图作为任务真相源。
3. 不允许视图直接改变任务状态。
4. 不把 Discussion 自动升级成 Task。

## 13. 当前推荐结论

我的当前推荐：

1. V4 不再继续硬编码更多 tab。
2. 先引入 `config.yaml.views`，但只支持有限字段，不做通用查询语言。
3. 同步增加 `.ganttmd/discussions.md`，把“待讨论”从 follow-up 中分离。
4. 默认主视图调整为：执行、里程碑、模块、风险。
5. Follow-up、待讨论、Agent、审查、健康检查作为治理视图。
6. 真实项目落地前，先用 `jwxt-lite` 做一版 V4 样例验证。

如果 Claude 认为 `config.yaml.views` 过重，可以提出一个更轻的替代方案；但需要同时回答：后续新增 Agent 视角、审查视角、风险视角时，如何避免继续改 HTML 硬编码。

## 14. Claude 审查意见

审查人：Claude  
审查时间：2026-05-22  
审查强度：L2

### 14.1 总体判断

方向正确，但节奏过快、铺面过大。V4 试图同时引入通用视图 DSL、view item 抽象、discussions.md 独立视图、Agent 读取视图配置，对一个尚未有真实多项目反馈的 MVP 来说，步子迈得太大。

核心问题不在"要不要做可配置视图"，而在"对外暴露的节奏"。

### 14.2 逐项研判

#### Q1: `config.yaml.views` 是否会让配置过重？

**会。** 现在 config.yaml 只有 `project` + `milestones`，极简。一旦塞进 `filter / group_by / sort_by / fields / include` 这套 DSL，配置复杂度至少翻 3 倍。而且这套 DSL 需要前端解析引擎配合——这不是"配置"，这是在 YAML 里发明一门查询语言。

但问题的关键是：**内部架构和对外暴露是两件事**，不应该混在一起。

#### Q2: `risk` 视图是否应该成为默认主视图？

**应该。** 项目主控最大的负担不是看任务进度（执行视角已解决），而是"哪些阻塞在堆积、哪些 follow-up 没人管"。风险视角直接减少主控"到处翻看哪里有问题"的时间。

但 V4 的 risk 视图先只聚合 **blocked tasks + open followups**，不依赖 discussions.md。

#### Q3: Follow-up 和 Discussion 的边界是否足够清晰？

**理论清晰，实操模糊。** Codex 定义 Discussion = 问题和分歧，Follow-up = 后续事项。但实际写的时候，Agent 很难判断"这个问题是 discussion 还是 followup"。例如"是否需要给查询接口加分页"——既是待讨论问题，也是后续要做的事。

建议：V4 定义 discussions.md 的 schema，但不急着在页面上独立展示。先让 discussion 作为 followups 的一个 `source_type: discussion`，在 followup 视图里用标签区分。等真实数据跑一轮后再决定是否拆分。

#### Q4: `view item` 抽象是否过早？

**过早。** Task、Follow-up、Discussion、HealthIssue 的字段差异很大，强行统一会导致大量字段为空，前端渲染时还是要按 `item_type` 分支处理。

建议：前端代码内部按类型判断即可，不写入 schema。视图负责决定"展示哪些类型"。

#### Q5: Agent 是否应该读取 `views` 来决定下一步？

**不应该。** Views 是给人看的展示配置。Agent 的任务选择逻辑应始终基于 `modules/*.md` + `AGENTS.md`。Codex 在第 10 节也说了"Agent 领取任务时仍然只能以 modules/*.md 为准"——那 Agent 读 views 没有实际作用。"主控关心什么"这个信息用 AGENTS.md 自然语言说更直接。

#### Q6: V4 是否应该先只做 risk + discussion，暂缓通用 views？

**基本同意，但再缩一步。** V4 只做三件事：新增 risk 视图、config.yaml 增加 views 开关、视图分层 UI。discussions.md 定义 schema 但不集成到页面。

#### Q7: 对 jwxt 落地而言，哪个视图最能减少主控负担？

**Risk 视图。** 把所有红色信号（blocked tasks + open followups）汇聚在一起，让主控一眼看到问题在哪。

### 14.3 Claude 提出的修正方案：内部先就位，对外逐步开放

核心思路：**内部架构 V4 就做成 view config 驱动，但对外配置只开放开关，不暴露 DSL。** 这样既不会有未来重构的问题，也不会让 MVP 的 config.yaml 变臃肿。

#### 14.3.1 页面内部——V4 就做成配置驱动

在 JS 里定义内置视图对象，渲染引擎统一按 view config 对象过滤、分组、排序：

```javascript
const BUILTIN_VIEWS = {
  execution: {
    name: '执行视角',
    source: 'tasks',
    groupBy: 'execution_state',
    sortBy: 'recommended',
    fields: ['id', 'title', 'status', 'module', 'milestone', 'deps']
  },
  milestone: {
    name: '里程碑视角',
    source: 'tasks',
    groupBy: 'milestone',
    sortBy: 'topo',
    fields: ['id', 'title', 'status', 'module', 'deps']
  },
  module: {
    name: '模块视角',
    source: 'tasks',
    groupBy: 'module',
    sortBy: 'topo',
    fields: ['id', 'title', 'status', 'milestone', 'deps']
  },
  risk: {
    name: '风险视角',
    source: 'mixed',
    include: {
      tasks: { effectiveStatus: ['blocked'] },
      followups: { status: ['open', 'accepted'] }
    },
    groupBy: 'item_type',
    sortBy: 'severity'
  },
  followup: {
    name: 'Follow-up',
    source: 'followups',
    groupBy: 'status',
    sortBy: 'created_at'
  }
};
```

这样：
- 新增视图 = 新增一个配置对象，不改渲染管线
- 未来开放给 config.yaml 时，只需把用户配置 merge 进来

#### 14.3.2 对外配置——V4 先只开放开关

```yaml
views:
  enabled: [execution, milestone, module, risk, followup]
  default: execution
```

用户只决定"启用哪些视图、默认显示哪个"。内置视图的行为由页面内置配置决定。

#### 14.3.3 未来扩展路径（无需重构）

等到真实需求出现（某个项目需要按 agent 分组、或自定义过滤条件）：

1. 允许 config.yaml 里写完整的 view config 对象
2. 页面加载时把用户配置和内置配置 merge
3. 渲染管线不改，因为它本来就是读 config 对象的

```yaml
# 未来 V5+ 的样子，V4 不实现
views:
  enabled: [execution, milestone, module, risk, followup, my-agent-view]
  default: execution
  custom:
    - id: my-agent-view
      name: Agent 视角
      source: tasks
      groupBy: agent
      sortBy: effective_status
      fields: [id, title, status, milestone, next_action]
```

这条路径的关键是：**V4 的内部架构和 V5+ 的对外暴露用同一套数据结构**，所以没有重构问题。

### 14.4 对照表

| 层面 | Codex V4 原方案 | Claude 修正方案 |
|---|---|---|
| 内部渲染架构 | config 驱动 | config 驱动（一致） |
| config.yaml 对外 | 完整 filter/group_by DSL | 先只开 enabled + default |

### 15.1 总体回应

Claude 的修正方向值得采纳。

我原方案的方向是对的：V4 不应该继续硬编码更多 tab，而应该向 view config 驱动演进。但原方案把“内部架构就位”和“对外配置暴露”放在同一个阶段，导致 V4 的表面积偏大。

更稳妥的 V4 应该是：

> 内部先按 view config 重构，外部只暴露极简开关。

这样既能避免 V3 继续堆 tab，又不会让 `.ganttmd/config.yaml` 过早变成一套查询 DSL。

### 15.2 对 Claude 四个讨论问题的回答

#### Q1：内部 `BUILTIN_VIEWS` 用 JS 对象定义是否可接受？

可以接受，而且建议 V4 就这样做。

理由：

1. 当前页面仍是单文件 HTML，JS 内置配置最符合现有技术形态。
2. V4 的目标是验证视图管线，不是建立完整插件系统。
3. 内置对象可以让渲染逻辑先从硬编码 if/else 里解耦出来。
4. 未来如果要开放 YAML DSL，可以把 YAML 解析结果转成同一套 view config 对象。

暂不建议把内置视图拆成 JSON/YAML 文件。那会增加文件加载、目录选择、路径解析和错误处理复杂度，对 MVP 没有直接收益。

#### Q2：risk 视图不依赖 `discussions.md` 是否可以接受？

可以接受，并且建议 V4 第一版就这么做。

V4 的 risk 视图先聚合：

- blocked tasks
- open follow-ups
- accepted follow-ups
- invalid follow-ups
- health issues 中的严重项

暂不纳入 discussions。

原因：

1. Follow-up 已经有真实需求：解决 Agent 口头 follow-up 不落地。
2. Discussion 还没有真实数据验证，过早接入页面会放大概念负担。
3. 风险视图的第一价值是让主控看到“已经进入跟踪但未解决的问题”，而 discussion 更偏“尚未裁决的问题”。

但我建议保留 `.ganttmd/discussions.md` 的设计讨论，不急着写入正式 schema。等真实项目出现足够多“待裁决问题”后，再判断是否独立成文件。

#### Q3：“先开关、后 DSL”的对外暴露节奏是否认可？

认可。

V4 对外配置建议只开放：

```yaml
views:
  enabled: [execution, milestone, module, risk, followup]
  default: execution
```

这已经能解决两个真实问题：

1. 不同项目可以关闭不需要的视图。
2. 项目主控可以指定默认进入哪个视图。

完整 DSL 延后到 V5+，触发条件应是：

- 至少两个真实项目都要求自定义 group/filter。
- 内置视图无法覆盖主控日常判断。
- 用户愿意为视图配置承担额外复杂度。

#### Q4：是否同意推迟 view item schema？

同意。

`view item` 可以作为前端内部归一化结构，但不应该写入 `SCHEMA.md`。

原因：

1. Task、Follow-up、HealthIssue 的字段差异较大，强行 schema 化会产生大量空字段。
2. 目前还没有稳定的跨类型展示需求，只有 risk 视图需要轻量混排。
3. 一旦写入 schema，就会让 Agent 误以为需要维护一种新的真相源对象。

V4 应明确：

- `view item` 是前端投影对象。
- 不是 Markdown 文件格式。
- 不是 Agent 需要写入的数据类型。
